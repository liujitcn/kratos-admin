# 日志与审计设计

> 状态：六类查询、关联审计、异步缓冲入库、菜单和归档任务已实施；故障演练持续完善。
> 日期：2026-08-31。
> 本设计不兼容旧的 `base_log` 查询接口，不迁移历史日志；实施时直接以 `v0.0.1` 的全新初始化数据为准。

## 1. 设计结论

日志审计拆分为六张互相独立的表，不建立公共日志父表，也不再通过一个 `log_type` 字段把不同事实混在一起：

```text
base_login_log
base_api_log
base_operation_log
base_data_access_log
base_permission_log
base_policy_evaluation_log
```

每张表只记录一种不可变事实：

| 表 | 回答的问题 | 典型生产者 |
| --- | --- | --- |
| `base_login_log` | 谁以什么方式尝试认证，结果如何 | 登录、退出、刷新令牌、MFA、OAuth |
| `base_api_log` | 哪个协议请求发生了什么 | HTTP/gRPC 统一访问中间件 |
| `base_operation_log` | 谁对哪个业务对象做了什么 | 业务 Case 或操作审计拦截器 |
| `base_data_access_log` | 谁访问了哪些数据，影响范围多大 | 数据访问层、导出/下载/查询服务 |
| `base_permission_log` | 权限配置发生了什么变更 | 角色、菜单、API、用户权限服务 |
| `base_policy_evaluation_log` | 鉴权引擎如何得出允许或拒绝 | Casbin/OPA 等鉴权引擎装饰器 |

`base_job_log` 继续作为定时任务执行日志存在，但不属于六类安全审计；运行日志文件也不落入这六张表。

## 2. 共同约束

### 2.1 事件不可变

- 审计表只追加，不提供编辑接口。
- 管理端只提供分页、详情和筛选，不提供新增、修改、删除按钮。
- 不使用 `updated_at`；`created_at` 表示落库时间，`occurred_at` 表示事件发生时间。
- 保留期到期后由后台归档或按时间批量清理，不通过普通租户 API 删除。
- 日志写入失败只记录指标和运行日志，不能改变原业务请求或鉴权结果。

### 2.2 租户和主体

- `tenant_id` 用于和当前业务表关联、筛选和数据隔离。
- `tenant_code` 必须同时保留，因为当前 Casbin 使用租户编码作为策略域。
- `user_id`、`user_name`、`role_id`、`role_code` 是事件发生时的快照，不能依赖后续关联表恢复历史信息。
- 登录失败可能无法解析出用户或租户 ID，此时允许主体字段为空，但应保存输入的租户编码、账号名和客户端信息。
- 普通租户没有日志菜单、查询 API 或详情 API 权限；平台管理员才可查询跨租户记录。

### 2.3 敏感数据

禁止记录密码、访问令牌、刷新令牌、私钥、验证码答案、完整 Cookie 和未脱敏请求体。

- 请求体、响应体只保留脱敏摘要；大字段不落库。
- 业务快照只保留允许审计的字段，密码、Token、密钥、验证码等字段统一删除或替换为 `[REDACTED]`。
- 策略输入保存 `input_hash` 和必要的脱敏摘要，不保存完整用户属性、请求头或 SQL 条件。
- 数据访问日志中的 SQL 只能保存脱敏后的文本和指纹；策略评估日志不保存 `scope_sql`。

## 3. 六张表结构

字段类型以 MySQL 为准，实际模型由 GORM 自动迁移产生；本设计不新增建表 SQL。

## 4. 枚举

枚举只放在实际使用它的 Proto 文件中，每个枚举值必须带中文注释：

| 枚举 | 建议值 |
| --- | --- |
| `BaseLoginLogType` | `UNSPECIFIED`、`PASSWORD`、`OAUTH`、`MFA`、`TOKEN_REFRESH`、`LOGOUT` |
| `BaseLogResult` | `UNSPECIFIED`、`SUCCESS`、`FAILURE`、`ERROR` |
| `BaseOperationAction` | `UNSPECIFIED`、`CREATE`、`UPDATE`、`DELETE`、`PUBLISH`、`REVOKE`、`IMPORT`、`EXPORT`、`OTHER` |
| `BaseDataAccessType` | `UNSPECIFIED`、`LIST`、`DETAIL`、`QUERY`、`EXPORT`、`DOWNLOAD`、`IMPORT` |
| `BasePermissionTargetType` | `UNSPECIFIED`、`USER`、`ROLE`、`MENU`、`API`、`TENANT` |
| `BasePermissionAction` | `UNSPECIFIED`、`GRANT`、`REVOKE`、`CREATE`、`UPDATE`、`DELETE`、`ASSIGN` |
| `BasePolicyEvaluationType` | `UNSPECIFIED`、`IS_AUTHORIZED`、`FILTER_PAIRS`、`FILTER_PROJECTS` |
| `BasePolicyDecision` | `UNSPECIFIED`、`ALLOW`、`DENY`、`ERROR` |

`reason_code` 使用字符串而不是跨表大枚举；原因由具体鉴权引擎或业务模块扩展，但对外只允许映射到项目冻结的错误语义。

## 5. 事件写入职责

```text
认证流程              -> base_login_log
协议请求中间件         -> base_api_log
业务 Case              -> base_operation_log
数据访问/导出层        -> base_data_access_log
角色/菜单/API 权限变更  -> base_permission_log
鉴权 Engine 装饰器      -> base_policy_evaluation_log
```

### 5.1 请求链路

同一个请求可以产生多条不同事实，但每条只写入所属表：

```text
请求进入
  -> base_api_log
  -> base_policy_evaluation_log
  -> base_data_access_log（实际访问数据时）
  -> base_operation_log（实际发生业务变更时）
```

权限配置变更只写 `base_permission_log`，不再同时复制到 `base_operation_log`；API 请求与鉴权事实仍分别保留。

### 5.2 策略评估记录粒度

- `IsAuthorized` 每次实际引擎调用产生一条记录。
- 多租户或多主体循环按实际评估租户/主体记录，保留同一 `request_id` 和 `trace_id`。
- `FilterAuthorizedPairs`、`FilterAuthorizedProjects` 记录聚合结果，不为每个候选项单独写行。
- 每次真实 `IsAuthorized` 引擎调用都记录一条，耗时只包围引擎调用，不包含后续业务处理。
- 写入采用异步缓冲或批量队列，日志故障不能让鉴权失败。

### 5.3 Core 审计事件处理（已完成）

Core 通过 `Core 日志流水线` 将访问与策略事实投递到 `Core 日志事件流`，再由 Core 消费者分别写入 `base_api_log` 和 `base_policy_evaluation_log`。Admin 业务中间件使用独立 `admin.log.event` 队列，由 Admin 消费者写入登录、操作、数据访问和权限日志。Admin 继续提供六张完整 GORM 模型并负责自动迁移，Core 只使用 API/策略日志的精简内部模型写入，不注册或迁移模型。

不得出现以下状态：

- 同一请求同时写入 `base_log` 和 `base_api_log`；
- `base_log` 继续作为“系统日志”菜单展示六类日志；
- 新的策略评估记录通过 `base_log.log_type` 伪装成授权日志。

Admin 中间件负责登录、操作、数据访问和权限等业务事实并自行异步入库；API 与策略评估事实由 Core 采集、投递并异步入库。队列不可用时记录投递错误，不回退到已删除的旧表。

六类审计日志一律异步入库：请求线程只向有界进程内缓冲做非阻塞投递，后台工作协程再完成脱敏、序列化和 Redis 队列 IO；只有 `Core 日志事件流` 与 `admin.log.event` 的消费者可以调用日志 Store。消费者将稳定队列消息编号映射为日志主键，同一消息在写库成功但 ACK 失败后重投时按已存在处理。缓冲区满、队列不可用或事件序列化失败时只记录运行日志，不允许阻塞请求或同步回退写库。

## 6. Core 与 Admin 的职责边界

### 6.1 `kratos-core` 负责

- 定义通用 `LogEvent`、事件类型、脱敏上下文和 `LogEmitter/LogSink` 接口。
- 在 HTTP/gRPC 传输层采集 API 请求事实。
- 在授权中间件内采集鉴权允许/拒绝和策略评估耗时；拒绝结果必须在中间件提前返回前完成采集，登录结果由 Admin 业务中间件记录。
- 通过 `Core 日志流水线` 投递并消费 `Core 日志事件流`，使用精简内部模型写入 `base_api_log` 和 `base_policy_evaluation_log`。
- 移除 `logging.Server` 对 `models.BaseLog` 的硬编码，并移除队列服务对 `BaseLogRepository` 的强制依赖。

Core 不依赖 `base_login_log`、`base_permission_log` 等 Admin 业务模型，也不提供日志菜单和管理端页面。

### 6.2 `kratos-admin` 负责

- 定义六张 `base_*_log` 表的完整 GORM 模型，统一负责模型注册、自动迁移和查询 Repository。
- 投递并消费 `admin.log.event`，异步写入登录、操作、数据访问和权限日志。
- 提供六组只读 Proto、查询服务、管理端页面、菜单和管理员权限。
- 保留 `base_job_log` 作为 Core 任务执行日志；它不属于六类安全审计。

### 6.3 目标数据流

```text
Core HTTP/gRPC 与认证/授权采集
  -> Core Core 日志流水线 进程内缓冲
Core Core 日志流水线 后台工作协程
  -> Core 日志事件流
  -> Core API/策略日志 Store
Admin 业务 Case 采集操作/数据/权限事实
  -> Admin LogSink 进程内缓冲
Admin LogSink 后台工作协程
  -> admin.log.event
  -> Admin 登录/操作/数据访问/权限日志 Repository
```

### 6.4 跨仓库实施顺序

1. 在 `kratos-core` 增加 `Core 日志流水线`，负责 API/策略事件的队列投递与异步入库，并移除旧 `base_log` 队列契约和仓储。
2. Admin 注册六张完整模型并负责自动迁移；Admin 自身注册 `admin.log.event` 消费者，异步写入其余四类日志。
3. Admin 删除 `BaseLogService`、`BaseLogCase`、本地 `base_log` 模型/Repository、旧页面和菜单；`OpsMonitoring` 改读 `base_api_log`。
4. 在 Admin 的 `v0.0.1` 保留六类菜单和权限初始化，不增加增量或建表 SQL。
5. 完成 Core 与 Admin 的生成、测试和 Redis/MySQL 联调。

## 7. Proto、服务和管理端

每张表对应一个只读管理服务，所有服务名使用 `Base` 前缀：

| 表 | Proto 服务 | 管理端 HTTP 前缀 |
| --- | --- | --- |
| `base_login_log` | `BaseLoginLogService` | `/api/v1/admin/base/login-log` |
| `base_api_log` | `BaseApiLogService` | `/api/v1/admin/base/api-log` |
| `base_operation_log` | `BaseOperationLogService` | `/api/v1/admin/base/operation-log` |
| `base_data_access_log` | `BaseDataAccessLogService` | `/api/v1/admin/base/data-access-log` |
| `base_permission_log` | `BasePermissionLogService` | `/api/v1/admin/base/permission-log` |
| `base_policy_evaluation_log` | `BasePolicyEvaluationLogService` | `/api/v1/admin/base/policy-evaluation-log` |

六个单表服务之外，`BaseLogService` 只提供跨日志表的公共关联查询 `GetBaseLogTrace`，不对应具体表。

每个服务第一版只提供：

- `PageBaseXxxLog`：按时间、租户、用户、结果和资源筛选；
- `GetBaseXxxLog`：查看脱敏后的详情。

`BaseLogService.GetBaseLogTrace` 按 `request_id` 或 `trace_id` 聚合六类审计记录，管理端在任一日志详情中按时间线展示同一请求的 API、鉴权、数据访问和业务事实。

不暴露 `Create` HTTP API。内部写入使用独立 writer/repository，避免审计接口被普通客户端调用。

管理端页面建议拆成六个菜单页面，列表页复用表格和详情抽屉组件，但每页使用自己的 Proto、字段和查询接口。策略评估页额外展示鉴权引擎、评估类型、资源、动作、决策和耗时。
