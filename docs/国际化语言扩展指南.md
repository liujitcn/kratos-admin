# 国际化语言扩展指南

本文是新增语言的执行手册。当前固定语言集合为 `zh-CN`、`zh-TW`、`en-US`、`ja-JP`。新增语言时，编译期语言包决定“代码能渲染什么语言”，`base_language` 数据只决定“当前部署启用什么语言、如何排序以及哪种语言是动态资源主语言”。

## 先理解两层职责

| 层 | 权威来源 | 作用 |
| --- | --- | --- |
| 编译期 | 后端错误目录、三端 core/System JSON、代码生成目录 | 语言白名单、固定 UI 文案、错误文案、代码生成模板 |
| 运行期 | `base_language` 表 | 语言名称、原生名称、启用状态、排序、主语言 |

因此只在数据库增加一条语言记录不能让页面出现新语言；只增加前端 JSON 也不能让动态菜单、字典和登录页读取到该语言。两层必须同步。

## 需要增加的文件

每个语言代码都必须在以下七个语言包目录使用同名 JSON 文件；代码生成器另有一个统一的 `catalog.json`：

| 目录 | 内容 |
| --- | --- |
| `backend/internal/i18n/assets` | 后端错误消息目录 |
| `frontend/admin/packages/core/src/locales` | 管理端底座和公共文案 |
| `frontend/admin/packages/modules/system/src/locales` | 管理端 System 文案 |
| `frontend/uni-app/packages/core/src/locales` | uni-app 底座和公共文案 |
| `frontend/uni-app/packages/modules/system/src/locales` | uni-app System 文案 |
| `frontend/taro-app/packages/core/src/locales` | Taro 底座和公共文案 |
| `frontend/taro-app/packages/modules/system/src/locales` | Taro System 文案 |
`backend/internal/biz/system/admin/codegen/locales/catalog.json` 不是语言包目录，而是按语言代码组织的代码生成器模板和静态术语数据。

JSON 的 key、占位符和命名空间必须保持不变。`common.language.<locale>` 用于离线显示语言名称，可以补充；运行时名称优先从数据库读取，因此新增语言不需要修改已有语言包或 TypeScript 注册代码。

## Key 命名速查

新增固定文案时，先确定所属模块和组件，再按统一规则命名：

```text
前端：<模块>.<defineOptions.name 转换路径>.<文案类型>.<名称>
后端：<package 去掉版本>.<Service 转换路径>.<操作或对象>.<字段>.<规则>
```

示例：

```text
BaseDict -> system.base.dict.dialog.confirm_status
BaseDictService / system.admin.v1 -> system.admin.base.dict.create.name.required
CodeGenTable -> system.code.gen.table.field.page_type
```

组件名和 Service 名按 PascalCase 拆成小写点号路径；末端名称、字段和规则统一使用 `snake_case`。跨业务公共文案使用 `common.*`，后端通用错误使用 `common.error.*`。后端 key 不带 `v1`；`message_key` 改名需要同步 Proto、Go 和全部语言目录。

## 标准流程

### 1. 选择语言代码

使用 BCP 47 形式，例如 `de-DE`、`pt-BR`。语言代码必须在全部目录一致，不能同时出现 `de`、`de-DE` 两种表示。代码需要能被 Core 的 `resource/i18n` 语言资源目录解析，并且管理端的 Day.js、Element Plus locale 依赖能找到对应区域或基础语言映射。

### 2. 增加语言包

以 `zh-CN.json` 为 key 基准，在上表七个目录增加 `<locale>.json`，逐项翻译 value：

```text
backend/internal/i18n/assets/de-DE.json
frontend/admin/packages/core/src/locales/de-DE.json
frontend/admin/packages/modules/system/src/locales/de-DE.json
frontend/uni-app/packages/core/src/locales/de-DE.json
frontend/uni-app/packages/modules/system/src/locales/de-DE.json
frontend/taro-app/packages/core/src/locales/de-DE.json
frontend/taro-app/packages/modules/system/src/locales/de-DE.json
```

代码生成器的 `catalog.json` 不是按文件拆分，而是在同一个 JSON 对象中增加 `"de-DE"`，字段必须完整保留：`menu`、`resource`、`password_strength`、`static`。

`common.language.<locale>` 可写入管理端 Core 语言包，用于离线显示语言名称和生成 `base_language` 迁移的初始名称；运行时语言名称、排序和启用状态仍以数据库记录为准。新增语言不需要修改已有语言包中的语言名称键。

翻译时必须保留 `{name}`、`{field}`、`{max}`、`{{.Value}}` 等占位符以及 URL、权限路径、字典 code/value 和 HTML/Markdown 标签。不要翻译路由 `name`、`path`、`component` 或 API 路径。

### 3. 运行同步脚本

在仓库根目录执行：

```bash
make i18n-sync
```

脚本会检查：

- 七个语言包目录的文件集合是否一致；
- 每个语言包的 key 集合和占位符是否一致；
- 代码生成器语言目录字段是否完整；
- 管理端 Day.js 和 Element Plus 是否存在可用映射。

检查通过后脚本生成以下文件，不要手工编辑：

- 六个前端包的 `src/locales/generated.ts`；
- 管理端 Day.js、Element Plus locale 映射；
- 传入迁移版本时生成 `language.up.sql` 和说明文件。

### 4. 生成数据库语言记录

当前仓库统一使用 `v0.0.1` 迁移；生成语言初始化记录时写入该版本：

```bash
make i18n-sync I18N_MIGRATION_VERSION=v0.0.1
```

脚本生成的迁移只负责补充 `base_language` 记录，使用 `INSERT IGNORE`，不会覆盖已有部署的启用状态、排序和主语言配置。提交前检查迁移版本目录，确保 `language.up.sql` 与说明文件一起提交。

如果部署不希望立即启用语言，可以在迁移后将 `base_language.status` 调整为禁用；主语言只能通过管理端语言配置或数据库配置切换，不能通过前端语言包改变。

### 5. 准备动态资源译文（可选）

固定 UI 和后端错误包完整后，新语言即可在运行时回退主语言。若要为内置菜单、字典、字典项和系统配置提供固定译文，可以使用批量脚本生成语言包和动态翻译数据：

```bash
I18N_OFFLINE=1 \
make i18n-locale I18N_LOCALE=de-DE
```

联网翻译可去掉 `I18N_OFFLINE=1`。该命令默认写入 `v0.0.1` 下的对应语言包、`i18n.de-DE.up.sql` 及说明文件。迁移只写入非空固定文本，已有值不会覆盖；若语言包已经人工完成，直接维护 `i18n.<locale>.up.sql`，不要用该命令覆盖人工译文。

动态资源也可以在管理端国际化维护页面中编辑。表单中有内容的主语言文本可单独或批量即时翻译，Draft 接口只返回单个译文、不写入统一国际化表；人工输入会直接保存到统一国际化表。空译文在资源创建或更新成功后进入异步国际化队列，提交空文本时也会按保存逻辑补齐，失败消息由定时任务再次扫描，已有非空译文不会覆盖。国际化接口只有在 `I18N_DRAFT_ENABLED=true` 或等价应用 metadata 开启时可用。系统配置名称以及文本、富文本类型的值支持国际化，图片和布尔值不外发；运行时值缺失时回退主语言。

### 6. 验证并提交

推荐在提交前执行：

```bash
make i18n-check
make i18n-sync
git diff --check

cd backend && go test ./...
cd ../frontend/admin && pnpm type:check && pnpm lint:oxlint
cd ../uni-app && pnpm tsc && pnpm lint
cd ../taro-app && pnpm tsc && pnpm lint
```

确认新增语言在以下场景可用：首次启动、登录前语言切换、登录后切换、刷新恢复、动态菜单、字典展示、校验错误和缺少动态译文时的主语言回退。

## 不需要修改的内容

新增语言不需要修改：

- Go locale 常量、后端服务注册和错误本地化代码；
- 三端 locale runtime、模块注册和请求封装；
- Proto、RPC 生成文件和菜单路由代码。

这些运行时文件读取编译期语言包和同步脚本生成的前端注册文件；运行时启用语言、默认语言和排序由 `base_language` 数据库记录提供。只有在新增语言暴露出基础库没有 locale 映射、语言包结构需要新增字段或业务确实增加新翻译 key 时，才需要相应依赖或代码变更。

## 故障排查

| 现象 | 检查 |
| --- | --- |
| `语言集合不一致` | 七个语言包目录是否都存在同名 JSON |
| `语言键集合不一致` | 与同目录 `zh-CN.json` 比较 key 和占位符 |
| `代码生成器语言目录字段不完整` | `catalog.json` 是否包含四个固定字段及完整子字段 |
| `缺少组件语言映射` | Day.js/Element Plus 是否提供该区域或基础语言文件 |
| 语言能切换但名称为空 | 检查 `base_language` 记录，或补充 `common.language.<locale>` |
| 菜单/字典仍显示主语言 | 检查统一翻译表是否存在非空记录，以及请求是否发送 `Accept-Language` |

完整架构说明见[国际化最终方案](国际化最终方案.md)；语言包目录的局部约束见各目录 README。
