# 工作流接入指南

本文说明 kratos-admin 审批工作流的能力边界，以及本仓库页面与其他项目（宿主，如 cloud-scp）接入业务单据审批的方式。

## 能力概览

- 流程定义：`workflow_definition`，节点图 JSON（version 2）+ 申请表单定义 JSON；草稿可编辑，启用时校验图结构，编码+版本唯一且不可修改，仅草稿可删除。
- 流程实例：`workflow_instance`，状态机 审批中 → 已通过 / 已驳回 / 已撤回。
- 节点类型：开始/结束、脚本计算、审批任务（会签 ALL / 或签 ANY，审批人 用户/角色/岗位）、排他网关（expr 表达式 + default 边）、并行分支/汇聚。
- 审批动作：通过、驳回（任一驳回整单终结）、转办、加签；申请人可撤回；审批委托在解析审批人时替换。
- 终态副作用：站内信通知申请人（消息分类 `WORKFLOW`）+ 业务终结回调（见下）。工作流消息的 `source` 按业务类型区分：租户审批为 `tenant`、租户项目审批为 `project`，其他审批默认使用 `workflow`。
- 超时催办：定时任务 `system.admin.WorkflowTimeout`（每小时）扫描待办，超 24 小时催办提醒办理人，超 72 小时升级提醒办理人与申请人；升级只追加通知不自动转办（部门暂无负责人字段，避免自动夺权），各待办催办、升级仅一次。
- 引擎安全语义：非脚本首次推进失败 fail-closed 整单驳回，脚本节点执行失败保留记录并暂停；并行分支全部展开后检查终态，汇聚未满不提前判通过；审批动作在实例锁内重新核验任务与办理人；通知与业务回调仅在事务成功提交后执行。
- 待办权限：按当前租户内的申请人/办理人授权，不沿用任务记录的 `created_by` 数据范围；租户隔离仍然生效。

## 宿主项目接入

宿主项目依赖 `github.com/liujitcn/kratos-admin/backend` 并注册 Admin 模块后，引擎随模块装配自动就绪（`pkg/workflow.SetDefaultEngine` 在 `NewWorkflowInstanceCase` 构造时注入）。接入只需三步：

### 1. 提交审批（正向）

在业务单据提交的 Case 中调用包级函数；租户与申请人缺省取请求上下文登录态，也可显式指定：

```go
import pkgWorkflow "github.com/liujitcn/kratos-admin/backend/pkg/workflow"

instanceID, err := pkgWorkflow.Submit(ctx, pkgWorkflow.SubmitParams{
    Code:         "EXPENSE",   // 流程定义编码（须已启用）
    Version:      1,
    FormData:     formDataJSON, // 与表单定义/网关条件对应的 JSON
    BusinessType: "EXPENSE",   // 业务单据类型，回调分发键
    BusinessID:   expenseID,
    OnCreated: func(bindCtx context.Context, instanceID int64) error {
        // 宿主在自己的事务内保存实例 ID 和“审批中”状态，提交成功后返回。
        return expenseRepo.BindWorkflow(bindCtx, expenseID, instanceID)
    },
})
```

`BindWorkflow` 是宿主自行实现的单据回写方法。引擎先提交实例创建，随后调用 `OnCreated`，宿主自行完成并提交关联回写；两者不共享私有事务。不要在外层另开事务包装 `Submit`。`OnCreated` 失败时引擎将未推进实例终结为已驳回并返回错误，不创建待办或触发业务回调。

存在业务单据关联时必须在 `OnCreated` 中保存实例 ID 和“审批中”状态，不能等 `Submit` 返回后再回写。开始节点直达结束节点、审批人全为申请人，以及首次推进失败的流程，都可能在 `Submit` 返回前同步终结；引擎等待关联回写成功后才推进并触发回调。提交成功后不要再次把单据状态覆盖为“审批中”。

有 `OnCreated` 时，必须在宿主启动装配阶段按业务类型注册只读绑定核验器，注册完成后再接受提交：

```go
pkgWorkflow.DefaultEventRegistry().RegisterBindingVerifier("EXPENSE", func(
    verifyCtx context.Context, tenantID, instanceID, businessID int64,
) (bool, error) {
    // 宿主方法按租户和单据编号查询已提交关联，并确认实例编号完全一致。
    return expenseRepo.IsWorkflowBound(verifyCtx, tenantID, businessID, instanceID)
})
```

`IsWorkflowBound` 是宿主实现的只读查询，不能在核验器中补写关联、重新提交或触发业务动作；查询错误应原样返回。引擎在恢复或人工重试未确认的 START 时调用核验器，只有返回 true 才允许继续推进。false/错误保留实例 PENDING，将 START 记为 FAILED 并退避等待重试；宿主应检查绑定状态后修复原因，不应另建重复申请。

### 2. 注册终结回调（反向）

在宿主模块初始化（wire 构建后执行一次即可）注册业务回调；引擎在实例到达已通过/已驳回/已撤回且对应事务成功提交后同步触发：

```go
func init() { // 或模块装配处
    pkgWorkflow.DefaultEventRegistry().Register("EXPENSE", onExpenseTerminal)
}

func onExpenseTerminal(ctx context.Context, tenantID, instanceID, businessID int64, status adminv1.WorkflowInstanceStatus) {
    // 铁律一：校验回调参数与单据回写的 instanceID 一致，防止伪造 business 字段触发他人单据副作用。
    // 铁律二：只处理"审批中"的单据，重复回调幂等跳过。
    // 通过 → 单据置已通过（如需扣减额度在此执行）；驳回/撤回 → 同步终态。
}
```

回调 panic 由引擎 recover 隔离，不影响状态机；回调失败自行记日志重试。

### 3. 查询单据关联状态（展示）

```go
status, err := pkgWorkflow.StatusByBusiness(ctx, tenantID, "EXPENSE", expenseID)
// status.InstanceID / status.Status / status.EndAt
```

宿主也可实现 `pkg/workflow.Engine` 接口后 `SetDefaultEngine` 替换默认实现（如测试桩）。

## 本仓库页面

系统管理 → OA 审批：审批中心（待办/已办/我发起、发起申请、审批四动作、撤回、节点任务进度）、流程定义（列表 + SVG 设计器 + 表单定义）、审批委托。接口见 `api/proto/system/admin/v1/workflow_*.proto`。

## 约束与边界

- 宿主业务模块与本仓库引擎同进程调用，不经过 HTTP/gRPC；`backend/internal` 对外不可导入，宿主只能使用 `backend/pkg/workflow` 公共面。
- 委托为单跳替换（被委托人再设委托不递归生效）；转办/加签目标必须为启用用户。
- 子流程（`workflow_parent_link` 表已建）暂未实现。
- 存量数据库不会自动重放 `v0.0.1` 初始化脚本，新菜单需按开发环境流程重建库或手动补种。

## 脚本与可靠业务动作

流程执行与专用试跑只允许启用的 JavaScript 脚本，通过独立 goja 沙箱执行，不开放 process、require 等宿主能力；每次运行使用独立状态并支持超时硬中断。共享脚本管理仍保留原有九种语言；专用试跑只能引用已保存脚本，不接受任意源码或语言参数。

节点图保持 version 2。`hooks.before_submit/approved/rejected/withdrawn` 引用脚本 ID；`SCRIPT.script_id` 执行变量计算；`TASK.approver_script_id` 与静态 `approvers` 二选一。脚本库是系统共享能力，发布时服务端从启用脚本重建 `script_snapshots`，并固定名称、语言、版本、源码。实例再保存自己的图快照和 `variables`，修改脚本库或定义不能改变进行中的审批。详情返回的节点图会隐藏脚本源码。

统一输入为 `{form, variables, workflow, node, idempotency_key}`，其中 workflow 包含 instance_id、tenant_id、applicant_user_id、business_type、business_id、status，node 包含 id、type。JavaScript 可用最后一个对象表达式作为输出：

| 阶段 | 输出 |
| --- | --- |
| 提交前 | `{allowed: true, variables: {validated: true}}`，拒绝时返回 allowed:false 与 message |
| SCRIPT 节点 | `{variables: {total: ctx.form.amount * 2}}` |
| 动态审批人 | `{user_ids: [2, 3]}` |
| 已通过/已驳回/已撤回 | `{variables: {...}, actions: [{type: "expense.approve", payload: {...}}]}` |

网关可继续使用 `amount > 1000`，也可使用 `variables.total > 1000`。动态审批人必须为本租户启用用户，委托目标同样校验；空列表、非法用户或执行异常会保留失败记录并暂停流程，不会因没有待办而误判通过。提交前拒绝不会创建实例，仍保留统一脚本日志。

宿主在启动装配时显式注册动作白名单。例如下面代码可直接接入宿主已有的事务方法：

```go
// ExpenseEffects 由宿主实现：在同一数据库事务中校验租户和实例关联、写幂等记录并更新单据。
type ExpenseEffects interface {
    ApplyWorkflowAction(context.Context, pkgWorkflow.ActionContext, string) error
}

// RegisterExpenseActions 注册允许脚本调用的报销动作。
func RegisterExpenseActions(effects ExpenseEffects) {
    registry := pkgWorkflow.DefaultEventRegistry()
    registry.RegisterAction("EXPENSE", "expense.approve", func(ctx context.Context, action pkgWorkflow.ActionContext) error {
        return effects.ApplyWorkflowAction(ctx, action, "expense.approve")
    })
    registry.RegisterAction("EXPENSE", "expense.close", func(ctx context.Context, action pkgWorkflow.ActionContext) error {
        return effects.ApplyWorkflowAction(ctx, action, "expense.close")
    })
}
```

`ActionContext` 包含 TenantID、InstanceID、BusinessID、BusinessType、Status、IdempotencyKey、Payload。宿主必须使用 TenantID 查单据，并确认单据绑定的流程实例等于 InstanceID；根据真实业务状态和字段规则重新校验 Payload，不能直接信任脚本传入的扣款金额。以 `IdempotencyKey` 建唯一索引，并将幂等记录与业务变更放进同一事务；重复键返回成功。若需要调用外部支付或消息服务，向该服务传递相同幂等键，或在宿主事务中落自己的 outbox。进程可能在外部副作用成功后、引擎保存动作进度前退出，因此仅依赖引擎的已完成动作数不能保证外部副作用恰好一次。

终态脚本任务在审批事务中落库，事务提交后执行；动作失败不撤销审批结果。执行记录状态为 PENDING/RUNNING/SUCCEEDED/FAILED/CANCELED；阶段为 BEFORE_SUBMIT/NODE/APPROVER/APPROVED/REJECTED/WITHDRAWN。终态动作保存逐项进度，重试跳过已完成动作，当前失败动作使用稳定幂等键。旧式 `Register` 终结回调仍可用于展示或通知，不能与业务动作重复执行扣款、记账等副作用；可靠副作用应使用可返回错误的动作处理器。

分钟扫描恢复待执行及失败记录，自动尝试最多 5 次并指数退避；人工重试不受累计次数限制。审批详情显示运行记录、输入输出、错误和下次重试时间。申请人、任务参与者或拥有管理数据范围的用户可在本租户重试：`PUT /api/v1/admin/workflow/instance/{instance_id}/script-run/{id}/retry`。撤回或驳回会取消未完成的节点执行，扫描与重试不得复活终结流程。

完整配置及脚本见 [脚本报销示例](../backend/testdata/workflow/script-expense/README.md)。

### 内置站内信动作

`workflow.notify` 可直接调用已装配的站内信模块，无需宿主注册动作处理器。终态脚本例如：

```javascript
({actions: [{type: "workflow.notify", payload: {
  title: "审批结果", content: "您的申请已处理",
  user_ids: [ctx.workflow.applicant_user_id]
}}]})
```

标题、正文与 user_ids 必填；受众限定为当前租户启用用户，重复用户自动去重，非法或跨租户受众在发布前拒绝。消息分类固定为 `WORKFLOW`、来源为 `workflow`，消息幂等键为 `workflow:` 加稳定动作键的 SHA-256 十六进制摘要，总长 73 字符；失败重试沿用相同消息键，复用现有消息模块的持久化幂等存储。已完成的动作不会重复发布。完整脚本见 [notify.js](../backend/testdata/workflow/script-expense/notify.js)。

工作流引擎产生的待办、转办、加签、驳回、通过和超时提醒会自动发布 `WORKFLOW` 站内信。消息动作统一使用 `MESSAGE_INBOX`，参数中的 `admin.route` 为 `WorkflowApproval`，并携带 `task_id` 或 `instance_id`；管理端通知中心据此直接打开审批详情，缺少或非法参数时回退到收件箱。

动作执行上下文超时为 45 秒，持久化租约为 60 秒。宿主处理器必须将传入 ctx 继续传递给数据库、HTTP 等调用并及时响应 ctx 取消，不能启动脱离 ctx 的后台副作用；外部服务仍需接收稳定幂等键，以覆盖网络超时、崩溃或租约接管时无法确认结果的窗口。

启动恢复使用执行记录的 `START` 阶段（`script_id=0`），不执行脚本，也不写共享脚本日志。无 `OnCreated` 或已持久化确认关联的启动中断可由分钟扫描恢复。有 `OnCreated` 时宿主必须注册 `RegisterBindingVerifier`，扫描对未确认关联先读取宿主持久化绑定：返回 true 才恢复；返回 false 或错误时将 START 记录设为 FAILED 并退避，实例保留 PENDING，不推进流程、不执行副作用。人工重试同样必须核验；不能仅因确认未落库或超时关闭申请，因为宿主可能已经提交关联。只有 `OnCreated` 明确返回错误才中止未推进申请，且不触发业务动作。
