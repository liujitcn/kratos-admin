# セキュリティポリシーと運用タスク

## ログインセキュリティ

ログインポリシーはグローバル、テナント、ユーザーのスコープごとに保存します。各スコープには 1 つのポリシーがあり、ポリシー配下のブラックリスト/ホワイトリスト制限はルール単位で保存します。実行時判定に参加するのは一致した有効ポリシーだけです。ユーザー、テナント、グローバルの順に、失敗時のロックとパスワード有効期間を上書きし、さらにログイン元制限を適用します。一致する有効ポリシーがない場合は、ログイン失敗ロック、パスワード有効期間、ログイン元制限を実行しません。

ポリシーを有効にすると、`max_failed_attempts`、`lock_duration_minutes`、`password_max_age_days` がそれぞれログイン失敗ロックとパスワード有効期間を制御します。`password_max_age_days` が `0` の場合、パスワード有効期間は無効です。有効なポリシーがない場合、これらのフィールドは適用されません。

MAC 制限はクライアントが送信する `X-MAC-Address` リクエストヘッダーに一致します。通常の HTTP から実際のネットワークカード MAC を取得することはできません。地域制限は信頼されたゲートウェイが注入する `X-Region-Code` リクエストヘッダーに一致し、ゲートウェイは外部から偽造された値を削除する必要があります。

パスワードポリシーは `BaseLoginPolicy` のグローバル、テナント、ユーザースコープで設定し、ユーザー追加、リセット、個人変更では現在のアカウントに適用されるポリシーを共通して読み取ります。パスワードの複雑度は小文字、大文字、数字、記号の 4 種類で計算します。

パスワードポリシーのフィールドは次のとおりです。

| フィールド | 既定値 | 説明 |
| --- | ---: | --- |
| `password_min_length` | `8` | 最小文字数 |
| `password_history_count` | `3` | 重複を禁止する履歴パスワードの保持数。`0` は無効 |
| `password_min_complexity_classes` | `3` | 小文字、大文字、数字、記号のうち必要なカテゴリ数 |
| `password_max_age_days` | `90` | パスワード有効期間。`0` は無効 |
| `initial_password` | 未設定 | パスワードなしでユーザーを追加した場合に使用。初回ログイン時に変更が必要 |

## 現在のセッション

`BaseSessionService` は現在のセッションの表示と、すべてのセッションを失効させる API を提供します。ログイン時にサーバーはセッション作成時刻、トークン発行時刻、アクセス元、デバイス、最後の業務活動時刻を記録します。管理 API リクエストは活動時刻を更新しますが、リフレッシュトークンのリクエストはアイドル時間を延長しません。既定のアイドルタイムアウトは 30 分、絶対有効期間は 12 時間で、`authn.session` から設定します。

## 監査ログ

Core はリクエストとポリシーイベントを `Core ログイベントストリーム` に書き込み、Core のコンシューマーがそれぞれ `base_api_log` と `base_policy_evaluation_log` に保存します。Admin の業務イベントは独立した `admin.log.event` に書き込み、Admin のコンシューマーがデータベースへ保存します。6 種類の完全なログモデルと自動マイグレーションは引き続き Admin が提供します。6 種類のログはすべて非同期で保存し、キューに失敗してもリクエストスレッドで同期保存しません。通常のテナントにはログメニューと検索権限を付与しません。

Admin のログバッファが停止または満杯になった場合、キューが利用できない場合、または配信に失敗した場合は、非表示システム設定 `baseLogFallback.file_path` に従って固定ファイル `admin-log.jsonl` に保存し、ファイル同期を実行します。各レコードは実行時キーサービスから `kratos-admin:base-log-fallback/integrity` で派生したキーを使用して HMAC を生成します。ログ保存フォールバックファイルは `system.admin.BaseLogFallback` タスクが毎日ログテーブルへ再保存し、独立したログストレージとアラートを設定する必要があります。データアクセスログは実際の Proto レスポンスから返却フィールド範囲、レコード数、機密フィールドへのアクセス有無を抽出します。データ層の事実がない場合、SQL、テーブル名、SQL フィンガープリントを捏造しません。

ログ保存フォールバックのパラメータは非表示システム設定 `baseLogFallback` に保存し、システム設定サービスが統一管理してキャッシュを即時更新します。設定構造は次のとおりです。

```json
{
  "file_path": "./logs/base-log-fallback"
}
```

定期タスク `system.admin.BaseTableArchive` を有効にすると、毎日 03:30 に `base_table_archive` の有効なアーカイブ設定を読み込み、オンライン保持期間を超えたデータをテーブル単位で現在のデータソースのアーカイブテーブルまたは OSS にアーカイブします。アーカイブ検証が成功し、設定で許可されている場合だけオンラインレコードを削除します。通常のアプリケーションログのローテーションと圧縮は `kratos-kit/logger` が担当します。

## データベースバックアップ

データベースバックアップポリシーは `base_table_backup` に保存します。データベース接続は起動設定の `data.database` または `data.databases` を再利用し、有効状態と保持数はデータソースごとに管理します。毎日 02:00 に `system.admin.BaseTableBackup` を実行します。バックアップ整合性キーと暗号化キーはそれぞれ `kratos-admin:backup/integrity`、`kratos-admin:backup/encryption` で実行時キーサービスから派生し、サービスプロセスの環境変数から注入しません。

`base_table_backup.status` は実行可否を、`base_table_backup.retention_count` は保持数を制御します。バックアップは統一して圧縮、暗号化し、OSS にアップロードします。

タスクは AES-256 でバックアップを暗号化して OSS にアップロードし、SHA-256、HMAC、オブジェクト情報を `base_table_backup_record` に保存します。OSS オブジェクトを読み戻して検証してから成功に変更し、復元処理は存在しないバックアップや検証に失敗したバックアップを拒否します。バックアップと復元はサービスプログラムが制御し、キーをサービスプロセスの環境変数やコマンドライン引数に出力しません。

復元は管理端末の `BaseTableBackupRestoreService.ExecuteBaseTableBackupRestore` から統一して実行します。プログラムは検証済みバックアップを OSS からダウンロードし、整合性検証、復号、展開、インポートを行います。復元前には業務書き込みを停止し、分離環境で復元演習を実施する必要があります。

OAuth クライアントの認証情報は、独立した `kratos-admin:oauth/credential-protection` 派生キーで暗号化して保存します。JWT キーのローテーションでこのキーを再利用しません。ポリシーへ移行した後、過去の平文 OAuth クライアントは管理端末の「クライアント認証情報をローテーション」で再生成する必要があり、旧平文認証情報には対応しません。

## オブジェクトストレージ

ファイルサービスは Core の OSS アダプターを再利用し、`local`、`aliyun`、`minio`、`s3` に対応します。単一インスタンスの開発環境では `local` を既定とし、ローカル OSS の `root_directory` を `/data/` の静的リソースパスへマッピングします。アップロード対象は `業務種別/ファイル分類/年/月/日/ファイル名` で保存し、データベースにはオブジェクトパスを保存します。複数インスタンスでは MinIO/S3 互換ストレージへ切り替え、設定したルートディレクトリと最小権限の認証情報を使用してください。Compose の MinIO は `object-storage` profile で起動します。

アップロード入口はファイル数、サイズ、拡張子を制限し、拡張子とサーバー側で判定した MIME の一致を検証します。HTML、SVG、PHP、Flash など実行可能または埋め込み可能な形式は拒否します。本番環境では `oss.upload_security` で ClamAV 互換スキャンコマンドを設定できます。ファイルが外部隔離領域へ入り、ゲートウェイがスキャンする場合は `SECURITY_EXTERNAL_FILE_SCAN=true` を宣言できますが、隔離、スキャン結果、許可ログは保持してください。

## 本番セキュリティ検証

独立サービスを `prod` または `production` で起動すると、データベース初期化前にセキュリティ基線を検証します。外部機能の宣言は次のとおりです。

| 変数 | 外部機能と必要な証跡 |
| --- | --- |
| `SECURITY_TLS_TERMINATED` | リバースプロキシまたはロードバランサーの TLS 設定、証明書、プロトコルスキャン結果 |
| `SECURITY_DATABASE_TLS_TERMINATED` | データベースプロキシまたはサービスメッシュの暗号化設定 |
| `SECURITY_REDIS_TLS_TERMINATED` | Redis プロキシまたはサービスメッシュの暗号化設定 |
| `SECURITY_EXTERNAL_BACKUP` | バックアップポリシー、遠隔コピー、復元演習、RPO/RTO 記録 |
| `SECURITY_EXTERNAL_LOG_ARCHIVE` | SIEM/WORM 保管ポリシー、アクセス制御、完全性証跡 |
| `SECURITY_EXTERNAL_FILE_SCAN` | 隔離領域、マルウェアスキャンポリシー、許可ログ |

外部プラットフォームが担当しない場合は、`base_table_archive` と `base_table_backup` にアーカイブおよびバックアップポリシーを設定し、非表示設定 `baseLogFallback` にログ保存フォールバックを設定し、`oss.upload_security` にスキャンコマンドを設定してください。本番検証は明らかな設定ミスを防ぐだけであり、等級保護評価、侵入テスト、運用制度の代わりにはなりません。

通常の HTTP API の既定リクエストボディ上限は 64 MiB、処理タイムアウトは 30 秒です。`server.http.max_body_bytes` と `server.http.timeout` で統一して設定します。`/events`、`/mcp`、AI メッセージストリームは既定ではリクエストタイムアウトを設定せず、HTTP リクエストボディ上限だけで保護します。ファイルアップロードには 1 ファイル 20 MiB、最大 20 ファイルの独立した制限があります。
