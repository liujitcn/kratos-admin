# ログと監査の設計

> 状態: 6 種類のログ検索、関連監査、非同期バッファ、メニュー、アーカイブタスクを実装済みです。障害訓練は継続して改善します。
> 日付: 2026-08-31。
> 旧 `base_log` 検索 API とは互換性がなく、履歴ログは移行しません。実装時は `v0.0.1` の初期化データを正とします。

## 1. 設計結論

監査ログは次の 6 つの独立テーブルに分割します。共通の親ログテーブルは作成せず、`log_type` で異なる事実を混在させません。

```text
base_login_log
base_api_log
base_operation_log
base_data_access_log
base_permission_log
base_policy_evaluation_log
```

各テーブルは 1 種類の不変な事実だけを記録します。

| テーブル | 記録する内容 | 主な生成元 |
| --- | --- | --- |
| `base_login_log` | 誰がどの方法で認証を試み、結果がどうだったか | ログイン、ログアウト、リフレッシュトークン、MFA、OAuth |
| `base_api_log` | どのプロトコルリクエストで何が起きたか | HTTP/gRPC 共通アクセス middleware |
| `base_operation_log` | 誰がどの業務オブジェクトに何を行ったか | 業務 Case、操作監査 interceptor |
| `base_data_access_log` | 誰がどのデータへアクセスし、影響範囲は何か | データアクセス層、エクスポート/ダウンロード/検索サービス |
| `base_permission_log` | 権限設定にどの変更があったか | ロール、メニュー、API、ユーザー権限サービス |
| `base_policy_evaluation_log` | 認可エンジンが許可または拒否を決めた過程 | Casbin/OPA などの認可エンジン decorator |

`base_job_log` は定期タスク実行ログとして引き続き存在しますが、6 種類のセキュリティ監査には含めません。

## 2. 共通制約

### 2.1 イベントは不変

- 監査テーブルは追記だけで、編集 API は提供しません。
- 管理端末はページング、詳細、絞り込みだけを提供し、追加、変更、削除ボタンは提供しません。
- `updated_at` は使用せず、`created_at` は保存時刻、`occurred_at` はイベント発生時刻を表します。
- 保持期間を過ぎたデータはバックグラウンドでアーカイブまたは時刻単位で一括整理し、通常のテナント API から削除しません。
- ログ保存失敗はメトリクスと操作ログだけを記録し、元の業務リクエストや認証結果を変更しません。

### 2.2 テナントと主体

- `tenant_id` で現在の業務テーブルと関連付け、絞り込み、分離を行います。
- 現在 Casbin がテナントコードをポリシードメインとして使用するため、`tenant_code` も保持します。
- `user_id`、`user_name`、`role_id`、`role_code` はイベント発生時のスナップショットです。後続の関連テーブルから履歴を復元しません。
- ログイン失敗時はユーザー ID やテナント ID を解析できない場合があるため、主体フィールドは空を許可します。ただし入力されたテナントコード、アカウント名、クライアント情報は保存します。

### 2.3 機密データ

パスワード、トークン、Cookie、秘密鍵、完全な OAuth 認証情報、完全な request/response body は保存しません。`base_data_access_log` は実際の Proto レスポンスからフィールド範囲、件数、機密フィールドへのアクセス有無だけを抽出します。データ層で事実を確認できない場合、SQL、テーブル名、SQL フィンガープリントを推測して記録しません。

## 3. 6 テーブルの構造

各テーブルは自身の業務事実を保持し、共通の親テーブルや汎用 `log_type` は追加しません。検索 API はテナント、時間、主体、结果、相関 ID を共通条件として使用し、詳細 API は保存済みスナップショットを返します。

### 3.1 `base_login_log`

ログイン、ログアウト、リフレッシュ、MFA、OAuth の成功・失敗を保存します。認証前に主体を特定できない場合は、入力されたアカウント、テナント、クライアント、IP、User-Agent を保存し、存在しない主体を推測しません。

### 3.2 `base_api_log`

HTTP、gRPC、MCP などのプロトコルアクセスを保存します。リクエストパス、メソッド、操作、状態、ステータス、処理時間、request/response サイズ、trace ID、エラー分類を記録します。body は機密情報を含むため、既定では保存しません。

### 3.3 `base_operation_log`

業務 Case または操作監査 interceptor が、作成、変更、削除、公開、復元などの業務操作を保存します。対象 ID、対象名、操作前後の安全な要約、操作結果、失敗理由、trace ID を保持します。

### 3.4 `base_data_access_log`

データアクセス、検索、エクスポート、ダウンロードの事実を保存します。Proto レスポンスから対象フィールド、レコード数、アクセス範囲、機密データへの到達有無を取得します。SQL 文字列や SQL fingerprint は、実際にデータ層から提供された場合だけ保存します。

### 3.5 `base_permission_log`

ロール、メニュー、API、ユーザー権限の付与、回収、変更を保存します。権限対象の種類、対象 ID、操作主体、変更結果を記録します。

### 3.6 `base_policy_evaluation_log`

認可エンジンの allow/deny 判定を保存します。主体、テナント、リソース、アクション、ポリシー結果、評価時間、失敗理由を保持し、秘密情報や完全なポリシー内容は保存しません。

## 4. 列挙型

ログ種別、端末種別、ログイン結果、操作アクション、権限対象、ポリシー判定、データアクセス範囲は Proto の列挙型を正とします。未知値は `UNSPECIFIED` または安全な内部値へフォールバックし、フロントエンドが任意の数値を表示名として解釈しないようにします。

## 5. イベント書き込みの責任

### 5.1 リクエスト経路

HTTP/gRPC の共通 middleware は request ID、trace ID、主体、テナント、開始時刻を取り込み、終了時に `base_api_log` へイベントを発行します。業務操作は Service のリクエスト変換ではなく、対応する Biz Case または監査 interceptor が `base_operation_log` を発行します。

### 5.2 ポリシー評価の粒度

認可判定 1 回につき 1 イベントを生成します。大量の内部ルール評価をそのままログへ出力せず、最終判定、主体、リソース、アクション、理由、相関 ID を保存します。

### 5.3 Core 監査イベント処理

Core は監査イベントを共通ストリームへ送り、Admin は自身の 6 テーブルへ非同期保存します。キュー障害は業務リクエストをブロックせず、メトリクス、警告、フォールバックファイルで追跡します。復旧タスクは保留イベントを再取得し、重複保存を避けるための冪等キーを使用します。

## 6. Core と Admin の責任境界

### 6.1 `kratos-core` の責任

Core はプロトコル middleware、主体・テナントのコンテキスト、共通イベント型、ストリーム、キュー、認可 interceptor を提供します。Admin 固有のテーブル、メニュー、業務名、管理画面を保持しません。

### 6.2 `kratos-admin` の責任

Admin は 6 種類の GORM モデル、マイグレーション、Repository、管理 API、メニュー、権限、検索条件、保管整理タスクを提供します。Admin 固有の業務イベントは `admin.log.event` から保存します。

### 6.3 目標データフロー

```text
HTTP/gRPC/MCP request
  -> Core context and interceptor
  -> Core audit event stream
  -> Admin consumer
  -> the six audit tables
```

### 6.4 リポジトリ横断の実装順序

まず Core のイベント契約とキュー境界を固定し、次に Admin の Proto、GORM、Service、Biz、データアクセス、メニュー、初期データを更新します。最後に三端の管理画面と国際化生成物を更新します。生成物は各リポジトリの既定コマンドで更新します。

## 7. Proto、Service、管理端末

各ログテーブルに Page、Get、必要な Option API を提供します。削除、編集、任意のログ書き換え API は提供しません。検索条件はテナント境界、時間範囲、主体、状态、操作、trace ID、target ID を組み合わせます。詳細画面は技術値をそのまま表示せず、言語パックと動的翻訳を使用します。

## 8. メニュー ID 計画

ログと監査は「システム管理 → ログ監査」の下に配置します。各ログ種別には一覧と詳細の権限を用意し、メニュー ID、親 ID、ロールのメニュー集合、`i18n.*.up.sql` の target ID を同時に更新します。

## 9. `v0.0.1` の変更範囲

テーブル、メニュー、API 権限、ロール集合、初期辞書、国際化 SQL は唯一の `v0.0.1` 初期化スクリプトで管理します。既存データベースは初期化スクリプトの変更を自動再実行しないため、検証は新規データベースまたは開発環境の再構築で行います。

## 10. 実施順序

1. Core のイベント契約、コンテキスト、キュー境界を固定します。
2. Admin の Proto、生成物、GORM、Biz、Service、Wire を更新します。
3. 管理 API、メニュー、権限、6 種類の一覧・詳細画面を接続します。
4. 保管期間、アーカイブ、フォールバック、アラートを検証します。
5. `make gen`、`make check`、`make i18n-check` を実行し、三端で言語切替、テナント隔離、機密フィールドの非表示を確認します。
