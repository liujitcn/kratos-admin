# Go 工作流引擎候选调研

> 调研日期：2026-10-20
>
> 状态：候选方案调研，不代表 `kratos-admin` 当前已实现的能力，也不替代代码、Proto、迁移和部署文档。
>
> 目标：对比 `go-wind-oa` 的自研 OA 审批引擎，判断 Go 生态中成熟方案是否能覆盖人工审批、持久化恢复、可视化和部署要求。

## 结论

没有找到一个“纯 Go、成熟、开箱即用，同时提供 BPMN/流程设计器、组织与候选人、人工任务列表、表单、审计和高可用”的方案。成熟度主要分成三类：

1. **Temporal/Cadence** 是 Go 一等公民的 durable execution 引擎，但人工审批只是 Signal/Update 或等待外部事件；审批任务、候选人、表单、权限、转办和待办 UI 仍要由业务系统实现。
2. **Conductor OSS** 的 `HUMAN` task 更接近人工审批，带服务端 UI 和 JSON 流程，但核心 Server 是 Java/JVM，Go 主要用于 SDK、Worker 和 API 接入。
3. **Camunda 8/Zeebe、Flowable** 的 BPMN User Task、Tasklist、表单和人工任务语义最完整，但平台是 JVM 体系；Camunda 官方 Go SDK 当前仍标注为 technical preview。

因此，`go-wind-oa` 的自研方案在 OA 领域贴合度和 Go 单体部署上有明显优势；外部引擎的价值主要在于长期运行、故障恢复、跨服务编排、重试/补偿、标准 BPMN 或现成运维界面。若主要需求是企业内部审批，优先增强自研内核；若审批只是复杂长事务的一部分，再考虑 Temporal；若必须要标准 BPMN 和现成 Tasklist，评估 Camunda/Flowable；若希望较少自建人工暂停逻辑且能接受 JVM，评估 Conductor。

## 对比基线：go-wind-oa

`go-wind-oa` 已将审批领域语义放进引擎，而不是只提供一个通用 DAG：流程定义使用 JSON 图，支持 `START`、`END`、审批任务、条件分支、并行分裂/汇聚和子流程；审批任务支持 `ALL` 会签与 `ANY` 或签；审批人支持用户、组织负责人和职位持有人；实例、任务、日志、并行汇聚、父子流程和委托均有持久化模型。引擎还处理撤回、转办、加签、审批委托、催办和超时升级，并通过业务事件回调同步请假、报销等单据状态。

这些语义来自项目自己的设计文档和实现：

- [工作流设计与数据模型](https://github.com/tx7do/go-wind-oa/blob/main/docs/oa-workflow-design.md)
- [图解析与校验](https://github.com/tx7do/go-wind-oa/blob/main/backend/app/core/service/internal/service/workflow_graph.go)
- [工作流服务实现](https://github.com/tx7do/go-wind-oa/blob/main/backend/app/core/service/internal/service/workflow_service.go)

自研方案的主要风险不在“能否走通一条审批链”，而在长期正确性：并发审批和幂等、服务重启后的恢复、定时器、历史归档、流程版本迁移、通知失败重试、租户与权限边界、可观测性、HA 和故障演练都需要项目持续维护。

## 候选方案

| 方案 | Go 位置 | 人工审批能力 | 持久化与恢复 | 可视化与部署 | 对 OA 的判断 |
| --- | --- | --- | --- | --- | --- |
| [Temporal](https://github.com/temporalio/temporal) | Go SDK 和 Server 都是一等公民 | 用 Signal/Update 或外部事件等待审批；没有原生候选人、组织、表单和待办模型 | Event History 持久化，Worker 可重放；生产部署使用 Temporal Service + MySQL/PostgreSQL/Cassandra 等 | Web UI 主要用于执行、History 和运维；可自托管或使用 Cloud | 最适合长时间等待、外部系统编排、重试/补偿；审批领域层仍需自建 |
| [Conductor OSS](https://github.com/conductor-oss/conductor) | 官方 Go SDK 用于定义/启动流程和 Worker；Server 是 Java 21 | 原生 `HUMAN` task，任务保持 `IN_PROGRESS`，通过 Task Update API 或事件完成 | 每个任务状态持久化，支持重试、暂停、恢复、终止；Server 有多种 DB/消息后端 | 自带 UI、REST/gRPC 和 CLI；核心平台是 JVM | 比 Temporal 更接近 OA 的“人工任务”，但需接受 Java Server、独立平台和自行接入组织权限 |
| [Camunda 8 / Zeebe](https://docs.camunda.io/docs/8.9/components/modeler/bpmn/user-tasks/) | 官方 Go SDK 当前为 technical preview；Go 也可通过 API 接入 | BPMN User Task、assignee、candidate users/groups、表单、Tasklist | Zeebe/Operate/Tasklist 等组件提供流程执行、持久化和运维能力 | BPMN Modeler、Tasklist、Operate 完整；自托管是 JVM/Kubernetes 体系 | 标准 BPMN 和人工作业能力最强，代价是平台复杂度和 Go SDK 稳定性风险 |
| [Flowable](https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs) | Java 引擎；Go 通常走 REST/独立 Java 服务 | BPMN User Task、用户/组任务、claim/complete、TaskService 和 REST API | 传统 BPMN 引擎，数据库、历史和任务服务成熟 | Java API、REST 和 Flowable 相关管理能力；不属于 Go-native | Java 技术栈中的传统 OA/BPM 强项；嵌入 Kratos 需要额外 JVM 服务 |
| [Dagu](https://github.com/dagucloud/dagu) | Go 单二进制，YAML DAG | 有 `human.task`，支持确认或 typed input，Web UI/CLI 可完成 | 默认本地文件存储，不需要外部 DB；支持 worker 部署 | 内置 Web UI，单机或 worker fleet；社区版 GPL-3.0 | 适合运维自动化和脚本编排；缺少 OA 的组织、候选人、会签、转办和业务表单语义 |
| [Argo Workflows](https://github.com/argoproj/argo-workflows) | Go/Kubernetes 原生 | `suspend` 可暂停，API/CLI/UI 可恢复；不是用户任务 | Workflow 状态和可选 Workflow Archive 可落 PostgreSQL/MySQL/MariaDB | Kubernetes 原生，UI 和 API 完整 | 适合容器、数据和 ML pipeline；不适合作为 OA 审批引擎 |
| [go-workflows](https://github.com/cschleiden/go-workflows) | 可嵌入 Go 的 durable workflow 内核 | 可用 Signal 等机制等待外部审批 | 官方 README 列出 SQLite、MySQL、PostgreSQL、Redis backend；状态以事件持久化 | 有诊断 Web UI 示例，无现成 OA 设计器/Tasklist/组织权限 | 可作为 Go 内核研究对象，但需要自己补齐 OA 领域和运维能力 |
| [go-workflow](https://github.com/go-workflow/go-workflow) | Go 工作流微服务 | JSON 流程、任务、候选用户/组、会签/或签、历史表，能力接近轻量 OA | README 描述 MySQL、流程实例/任务/IdentityLink/历史表和 K8s 部署 | 有独立 UI 仓库；项目定位明确为“超轻量” | 与 `go-wind-oa` 最接近，但主仓库最后代码提交可追溯到 2020-01，不能按持续维护的成熟平台评估 |

### Temporal：可靠的执行内核，不是 OA 产品

Temporal 官方 Go SDK 将 Workflow 定义为可持久化、可跨 Worker 恢复的协调逻辑，要求 Workflow 代码确定性、无副作用，副作用放在 Activity 中。Server 用事件历史重建状态，支持长时间 Timer、重试和 Worker 故障恢复。人工审批可以让 Workflow 等待 Signal 或 Update，再继续执行。

来源：

- [Temporal Go SDK README](https://github.com/temporalio/sdk-go)
- [Workflow programming model](https://github.com/temporalio/sdk-go/blob/master/workflow/doc.go)
- [Signal、Update、Query API](https://github.com/temporalio/sdk-go/blob/master/workflow/workflow.go)
- [Temporal architecture and event history](https://github.com/temporalio/temporal/blob/main/docs/architecture/README.md)
- [Self-hosted deployment](https://docs.temporal.io/self-hosted-guide)
- [Web UI](https://docs.temporal.io/web-ui)

引入 Temporal 后，`kratos-admin` 仍需有自己的 `workflow_task` 或审批域表，用于保存申请人、候选人/组织、表单、评论、权限和待办查询；审批动作再通过 Signal/Update 通知 Temporal Workflow。这样可以获得耐久执行，但不会自动得到 OA 的任务列表和组织模型。

### Conductor OSS：人工暂停更现成，但核心不是 Go

Conductor OSS 的 `HUMAN` task 会把流程停在 `IN_PROGRESS`，状态保存后等待外部 Task Update API 或事件完成；官方文档明确说明等待可以跨 Server 重启、部署和基础设施变化。Go SDK 负责注册 JSON 流程、启动实例和运行 Worker，Server 仍需要 Java 21。

来源：

- [HUMAN task](https://conductor-oss.github.io/conductor/documentation/configuration/workflowdef/systemtasks/human-task.html)
- [Human-in-the-loop guide](https://conductor-oss.github.io/conductor/devguide/ai/human-in-the-loop.html)
- [Conductor OSS server README](https://github.com/conductor-oss/conductor)
- [Conductor OSS Go SDK](https://github.com/conductor-oss/go-sdk)

它省掉了“Workflow 如何停下来等人”的底层实现，但 `HUMAN` task 本身不等于企业 OA：谁能看到任务、候选组如何解析、如何做租户隔离、表单和审批评论如何落库，仍需要在业务系统或 Conductor 周边实现。

### Camunda 8 / Flowable：BPMN 和人工任务最完整

Camunda 的 BPMN User Task 原生包含 assignee、candidate users/groups、forms 和调度属性，Tasklist 提供 claim/complete 和筛选，Operate 用于流程可视化与排障。Camunda 官方 Go SDK 页面当前标记为 technical preview，API 可能变化且不保证 SemVer。Flowable 的 BPMN User Task、TaskService 和 REST API 则是 Java 生态中的成熟路径。

来源：

- [Camunda User Tasks](https://docs.camunda.io/docs/8.9/components/modeler/bpmn/user-tasks/)
- [Camunda Tasklist](https://docs.camunda.io/docs/components/tasklist/userguide/using-tasklist/)
- [Camunda Go SDK 状态](https://docs.camunda.io/docs/apis-tools/go-sdk/)
- [Camunda self-managed reference architecture](https://docs.camunda.io/docs/self-managed/reference-architecture/)
- [Flowable BPMN User Task](https://www.flowable.com/open-source/docs/bpmn/ch07b-BPMN-Constructs)
- [Flowable TaskService API](https://www.flowable.com/open-source/docs/bpmn/ch04-API)
- [Flowable REST API](https://www.flowable.com/open-source/docs/bpmn/ch14-REST)

如果需求明确要求 BPMN 标准、拖拽设计器、现成 Tasklist、表单和组织任务语义，Camunda/Flowable 比 Go 自研或 Temporal 更省业务代码；代价是引入 JVM 平台、独立数据库/搜索/运维组件，并需要设计 Go 与引擎之间的边界。

### Dagu、Argo 与轻量 Go 内核

Dagu 的定位是本地优先的运维和内部自动化，虽然现在提供 `human.task`、Web UI 和 typed input，但它默认用文件保存状态，权限和高级自托管能力还受许可证/版本约束。Argo 的 `suspend` 是 Kubernetes 工作流暂停点，适合容器任务，不提供审批人、候选组、会签和业务表单。两者都不应直接替代 OA 审批域。

`cschleiden/go-workflows` 适合把 durable execution 嵌入 Go 服务，提供多种数据库 backend 和 Signal，但没有现成 OA 用户任务层。`go-workflow/go-workflow` 在数据模型上已经有流程定义、实例、任务、IdentityLink 和历史表，并以 JSON 取代 BPMN；不过其官方提交记录显示项目长期没有代码更新，适合参考模型，不适合作为新的企业基础设施依赖。

## 与自研方案的取舍

| 维度 | `go-wind-oa` 自研 | Temporal | Conductor | Camunda/Flowable |
| --- | --- | --- | --- | --- |
| OA 领域贴合度 | 高：审批人、会签/或签、委托、转办、表单和业务回调可直接建模 | 低到中：执行强，审批领域需自建 | 中到高：有 `HUMAN`，组织/权限仍需接入 | 高：BPMN 人工任务和 Tasklist 成熟 |
| Go 部署一致性 | 高：与现有 Kratos/Go 服务同栈 | 中：SDK/Worker 是 Go，但要运行独立 Temporal Service 和数据库 | 低到中：Go Worker + Java Server | 低：Java/JVM 平台 |
| 长时间等待与故障恢复 | 需要自行验证并持续维护 | 很强，事件历史和重放是核心能力 | 很强，任务状态持久化 | 强，成熟 BPMN 引擎能力 |
| 可视化 | 需要维护自己的编辑器、待办和历史页面 | 运维 UI，不是 OA 设计器/Tasklist | 有 UI，但组织待办需业务接入 | BPMN Modeler、Tasklist、Operate 最完整 |
| 运维成本 | 最低的服务数量，但可靠性由项目承担 | 需要数据库、Namespace、Worker 和服务运维 | 需要 JVM 服务、持久化/消息组件和 Go SDK | 需要多组件 JVM/K8s 或独立 Java 服务 |
| 可控性与定制 | 最高 | 执行模型稳定，业务语义需自建 | JSON 图和系统任务较灵活 | 受 BPMN 和平台边界约束 |

## 针对 `kratos-admin` 的建议

1. **主要是请假、报销、出差、用印等内部审批，流程拓扑相对稳定**：保留自研方向，抽出通用审批内核并重点补齐并发幂等、历史归档、通知重试、版本迁移、权限隔离和故障恢复测试。此时引入 Temporal 只为获得“等待审批”会增加平台复杂度。
2. **审批之外还要编排跨服务长事务、外部 API、补偿、重试、定时和人工等待数天**：评估 Temporal。建议保留业务侧审批任务/组织/表单表，Temporal 只承担耐久执行和状态推进，通过 Signal/Update 接收审批动作。
3. **产品要求标准 BPMN、拖拽设计器、现成 Tasklist/表单/Operate**：优先对 Camunda 8 与 Flowable 做 PoC，先验证 Go 调用链、租户隔离、数据同步、升级和 JVM 运维，不要把“官方 Go SDK”当作 Camunda 的成熟优势。
4. **希望直接使用现成 `HUMAN` task，同时能接受 Java Server**：评估 Conductor OSS。PoC 必须验证候选人/组织权限、审批动作审计、通知、租户和数据备份，而不只是验证流程能暂停和恢复。
5. **Dagu、Argo、`go-workflows`、`go-workflow`**：分别适合作业自动化、Kubernetes pipeline、嵌入式执行内核和轻量参考实现，不建议直接作为企业 OA 审批平台。

## 未纳入候选的 `go-zero-flow`

按 `go-zero-flow`、`zeromicro/go-zero-flow` 检索时，官方仓库 URL 在调研日返回 404；GitHub 上可找到的 [chenquan/zero-flow](https://github.com/chenquan/zero-flow) 描述为 go-zero 的 flow staining 实现，不是 OA 工作流引擎。因此没有把它当作成熟工作流平台参与比较。

## 参考：Cadence

[Cadence](https://github.com/cadence-workflow/cadence) 是 Uber 开源、与 Temporal 同类的 Go-native durable workflow 平台，支持 Signal 和独立的 Frontend/History/Matching/Worker 服务。它同样不提供 OA 原生 Tasklist、候选人、表单和组织权限。已有 Cadence 生态时可以继续使用；新项目通常优先评估 Temporal 的生态、文档和托管服务。

来源：[Cadence workflow engine](https://cadenceworkflow.io/docs/concepts/workflow-engine)、[Cadence Go Signals](https://cadenceworkflow.io/docs/go-client/signals)、[Cadence Go client](https://github.com/cadence-workflow/cadence-go-client)。
