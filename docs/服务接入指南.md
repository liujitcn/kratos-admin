# 服务接入指南

本文说明如何把一项新能力接入当前 Backend、管理端或应用端。只描述仓库已经采用的扩展方式。

## 先确定归属

| 场景 | 后端 Proto | 后端实现 | 前端 |
| --- | --- | --- | --- |
| admin、uni-app 与 Taro 共用 | `api/proto/base/v1` | `biz/base`、`service/base/v1` | 三端按需生成和封装 |
| 系统管理 | `api/proto/system/admin/v1` | `biz/system/admin`、`service/system/admin/v1` | System 模块 |
| 应用端系统能力 | `api/proto/system/app/v1` | `biz/system/app`、`service/system/app/v1` | uni-app 与 Taro |
| 独立业务模块 | 模块自有 Proto | 模块自有实现 | 独立管理端、uni-app 或 Taro 宿主模块 |

通用类型优先复用 Buf 中的 `common.v1`；System 跨端枚举放 `system/common/v1`。

## 内置后端能力

1. 有表结构变化时先更新开发库，再运行 `make -C backend gorm-gen`。
2. 定义 Proto、HTTP 映射、OpenAPI 描述和 `buf.validate`。
3. 运行 `make -C backend api` 和 `make i18n-openapi`，按消费端运行 `make -C backend ts`、`make -C backend ts-uni-app` 或 `make -C backend ts-taro-app`。
4. 在对应 `internal/biz/<proto-directory>` 实现业务，在 `internal/service/<proto-directory>` 实现 Proto 服务。
5. 把服务加入对应 `internal/server/{base/v1,system/admin/v1,system/app/v1}/register.go`。
6. ProviderSet 或构造参数变化后更新 `backend/wire.go` 并运行 `make -C backend wire`。
7. 在新迁移版本中补默认数据、菜单、按钮和服务方法权限。
8. 如果新增用户可见文案，同步对应模块的语言包，并执行 `make i18n-sync`。

生成目录是 `api/gen/go`、`internal/data/gen`、`internal/openapi/assets/openapi.yaml`、管理端、uni-app 和 Taro 包的 `src/rpc` 以及 `wire_gen.go`，不得手工编辑。

service 只做参数传递、日志和错误兜底；事务、租户、权限与状态规则放 biz；Repository 使用生成的类型化 Query，不拼接运行时 SQL。

## 外部 Go 模块

外部模块通过 `module.Resources` 提供业务构建前必须收集的静态资源：

```go
func NewModuleResources() module.Resources {
	return module.Resources{
		ProjectKey:  "order",
		ProjectName: "订单",
		Models:      orderdata.Models(),
		OpenAPI:     orderopenapi.Assets(),
		Docs:        orderdocs.Assets(),
		Migrations: []module.Migration{{Name: "order", FS: ordermigration.Assets(), Path: "."}},
		I18n:        orderi18n.Assets(),
	}
}
```

Core 会先根据静态资源初始化数据库、缓存、队列等基础设施。随后 Wire 构建模块 Case 和 Service，完整模块实现协议注册与运行期贡献：

```go
type Module struct {
	service orderv1.OrderServiceHTTPServer
}

func (m *Module) RegisterHTTP(server *http.Server) {
	orderv1.RegisterOrderServiceHTTPServer(server, m.service)
}

func (m *Module) registerAI(registrar module.AIRegistrar) error {
	return registrar.RegisterTools(module.AITerminalAdmin, m.agentTools...)
}

func (m *Module) Contributions() module.Contributions {
	return module.Contributions{
		AI: m.registerAI,
		/* Tasks、SSE、StartupHooks */
	}
}
```

组合根使用 `kratoscore.ProviderSet`、`kratoscore.BusinessProviderSet`、`NewModuleResources` 和模块业务 Provider；Core 通过公开的 `biz`、`biz/dto`、`config`、`module` 类型提供 BaseCase、Job、SSE、OpenAPI 和 Docs 能力，`internal` 目录只保留 Core 实现细节。

模块间调用只使用生成 gRPC Client。进程内可用 `Runtime.ClientConn()`，远程使用标准 gRPC 连接，调用代码不依赖 Backend `internal`。

## 数据库和权限

迁移目录：

```text
backend/migration/assets/vX.Y.Z/mysql/<feature>.up.sql
backend/migration/assets/vX.Y.Z/mysql/<feature>.description.md
backend/migration/assets/vX.Y.Z/mysql/<data-source>/<feature>.up.sql
```

管理端菜单 `component` 必须使用完整模块前缀，例如 System 页为 `system/base/user/index`。菜单 `api` 保存 Proto 服务方法标识，例如 `/system.admin.v1.BaseUserService/PageBaseUser`；HTTP 路径则由 OpenAPI 同步到 `base_api`。这两个概念不能混用。

## 管理端模块

当前默认业务模块是 `@liujitcn/kratos-admin-system`：

```text
frontend/admin/packages/modules/system/src
├── api
├── rpc
├── views
├── module.ts
└── index.ts
```

页面由模块名前缀隔离：

```ts
const views = import.meta.glob<{ default: Component }>("./views/**/*.vue");

export const orderAdminModule = defineAdminModule({
  name: "order",
  views
});
```

`views/list/index.vue` 对应菜单组件 `order/list/index`。模块还可以声明 `staticViews`、`headerTools`、`userMenuActions`、`routeOptions` 和命名 `extensions`。

宿主只在 `apps/admin/src/module-manifest.ts` 维护包名、加载器和可选预构建依赖。新增模块时同步增加宿主 `package.json` 依赖。模块不得使用 core 的私有 `@/*` 路径，只能引用 `@liujitcn/kratos-admin-core` 已公开子路径。

在本仓库中创建独立业务 workspace：

```bash
cd frontend/admin
pnpm module:create ../../../order-admin --module order
```

## 应用端宿主

应用端页面放在所属包的 `src/views`，同时通过模块的 `pages` 和 `views` 声明物理页面与稳定视图键。请求放在所属包的 `src/api`，业务类型来自生成的 `src/rpc`，页面不直接调用 `uni.request`。

外部宿主可使用：

```ts
const result = bootstrapKratosApp({
  app: App,
  pinia,
  modules: [{
    name: "order",
    pages: { "pagesOrder/list/index": {} },
    views: { ORDER_LIST: "pagesOrder/list/index" }
  }]
});
```

`KratosAppModule` 使用 `pages`、`views` 和可选 `icons` 描述模块页面。发布包的 `@liujitcn/kratos-uni-app-core/vite` 公开 `kratosApp()` 与 `createKratosUniPlugin()`；外部宿主在 Vite 配置中传入同一模块清单，即可复用页面扫描、wrapper 生成、静态资源合并和构建后恢复能力。

本仓库的接入示例位于 `frontend/uni-app/apps/uni-app/vite.config.ts`，同路径页面以宿主配置为准，后注册模块可覆盖先注册模块。

Taro 宿主使用 `defineKratosTaroModule()` 和 `defineKratosTaroBuildModule()` 同时声明运行时、页面和构建期入口，配置示例位于 `frontend/taro-app/apps/taro-app/src/module-manifest.ts`。模块页面由 `@liujitcn/kratos-taro-app-core/runner` 在构建期间装配，宿主不提交生成 wrapper 或页面配置。

## 验证

```bash
make i18n-check
cd backend && go test ./...
pnpm --dir frontend/admin check:exports
pnpm --dir frontend/admin lint:oxlint
pnpm --dir frontend/admin type:check
pnpm --dir frontend/uni-app test
pnpm --dir frontend/uni-app lint
pnpm --dir frontend/uni-app tsc
pnpm --dir frontend/taro-app test
pnpm --dir frontend/taro-app lint
pnpm --dir frontend/taro-app tsc
```

联调时检查动态菜单、按钮权限、租户数据范围、`/api/docs/openapi/{key}`、SSE/MCP，以及新迁移在空库和已迁移数据库上的行为。
