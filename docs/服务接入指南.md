# 服务接入指南

本文说明如何把一项新能力接入当前 Backend、管理端或应用端。只描述仓库已经采用的扩展方式。

## 先确定归属

| 场景 | 后端 Proto | 后端实现 | 前端 |
| --- | --- | --- | --- |
| admin 与 app 共用 | `api/proto/base/v1` | `biz/base`、`service/base` | 两端按需生成和封装 |
| 系统管理 | `api/proto/system/admin/v1` | `biz/admin`、`service/admin` | System 模块 |
| 应用端系统能力 | `api/proto/system/app/v1` | `biz/app`、`service/app` | `frontend/app` |
| 独立业务模块 | 模块自有 Proto | 模块自有实现 | 独立管理端或 app 宿主模块 |

通用类型优先复用 Buf 中的 `common.v1`；System 跨端枚举放 `system/common/v1`。

## 内置后端能力

1. 有表结构变化时先更新开发库，再运行 `make gorm-gen`。
2. 定义 Proto、HTTP 映射、OpenAPI 描述和 `buf.validate`。
3. 运行 `make api openapi`，按消费端运行 `make ts` 或 `make ts-app`。
4. 在对应 `internal/biz/<domain>` 实现业务，在 `internal/service/<terminal>` 实现 Proto 服务。
5. 把服务加入对应 `internal/server/{base,admin,app}/register.go`。
6. ProviderSet 或构造参数变化后更新 `wire.go`/`app.go` 并运行 `make wire`。
7. 在新迁移版本中补默认数据、菜单、按钮和服务方法权限。

生成目录是 `api/gen/go`、`internal/data/gen`、`internal/cmd/server/assets/openapi.yaml`、两个管理端包的 `src/rpc`、应用端 `src/rpc` 和 `wire_gen.go`，不得手工编辑。

service 只做参数传递、日志和错误兜底；事务、租户、权限与状态规则放 biz；Repository 使用生成的类型化 Query，不拼接运行时 SQL。

## 外部 Go 模块

外部模块实现 `core.Module`，只注册自己拥有的服务：

```go
type Module struct {
	core.ModuleAdapter
	service orderv1.OrderServiceHTTPServer
}

func (module *Module) RegisterHTTP(server *http.Server) {
	orderv1.RegisterOrderServiceHTTPServer(server, module.service)
}
```

通过 `kratosadmin.WithAdditionalModules(module)` 加入 Backend，或通过 `core.WithModules(module)` 直接加入 Core 宿主。需要运行时能力时实现对应 Contributor；数据库迁移通过 `kratosadmin.WithMigrations(...)` 注入。

模块间调用只使用生成 gRPC Client。进程内可用 `Runtime.ClientConn()`，远程使用标准 gRPC 连接，调用代码不依赖 Backend `internal`。

## 数据库和权限

迁移目录：

```text
backend/migration/assets/vX.Y.Z/mysql/<feature>.up.sql
backend/migration/assets/vX.Y.Z/mysql/<feature>.description.md
backend/migration/assets/vX.Y.Z/mysql/<data-source>/<feature>.up.sql
```

管理端菜单 `component` 必须使用完整模块前缀，例如 System 页为 `system/base/user/index`。菜单 `api` 保存 Proto 服务方法标识，例如 `/system.admin.v1.BaseUserService/PageBaseUser`；HTTP 路径则由 OpenAPI 同步到 `base_api`。这两个概念不能混用。

## 管理端模块

当前默认业务模块是 `@liujitcn/kratos-admin-system`：

```text
frontend/admin/packages/modules/system/src
├── api
├── rpc
├── views
├── module.ts
└── index.ts
```

页面由模块名前缀隔离：

```ts
const views = import.meta.glob<{ default: Component }>("./views/**/*.vue");

export const orderAdminModule = defineAdminModule({
  name: "order",
  views
});
```

`views/list/index.vue` 对应菜单组件 `order/list/index`。模块还可以声明 `staticViews`、`headerTools`、`userMenuActions`、`routeOptions` 和命名 `extensions`。

宿主只在 `apps/admin/src/module-manifest.ts` 维护包名、加载器和可选预构建依赖。新增模块时同步增加宿主 `package.json` 依赖。模块不得使用 core 的私有 `@/*` 路径，只能引用 `@liujitcn/kratos-admin-core` 已公开子路径。

在本仓库中创建独立业务 workspace：

```bash
cd frontend/admin
pnpm module:create ../../../order-admin --module order
```

## 应用端宿主

应用端页面放 `src/pages` 或 `src/pagesMember`，并同步 `src/pages.json`。请求放 `src/api`，业务类型来自生成的 `src/rpc`，页面不直接调用 `uni.request`。

外部宿主可使用：

```ts
const result = bootstrapKratosApp({
  app: App,
  pinia,
  modules: [{ name: "order" }]
});
```

当前 `KratosAppModule` 只有 `name`，只提供运行时具名注册，不包含页面、API、状态或组件自动发现。发布包的 `@liujitcn/kratos-app/vite` 目前只公开 Vite 配置类型、环境加载和 `createKratosUniPlugin()`；外部宿主需要自行维护页面接入。

本仓库 `frontend/app/vite.config.ts` 使用内部 `src/vite.ts#kratosApp()` 合并页面：同路径页面以宿主配置为准，缺失页面临时生成 wrapper，构建结束后恢复原文件。该函数当前没有作为 npm 子路径导出，不应在外部项目文档中宣称可直接调用。

## 验证

```bash
cd backend && go test ./...
cd frontend/admin && pnpm check:exports && pnpm lint:oxlint && pnpm type:check
cd frontend/app && pnpm test:vite && pnpm lint && pnpm tsc
```

联调时检查动态菜单、按钮权限、租户数据范围、`/api/docs/openapi/{key}`、SSE/MCP，以及新迁移在空库和已迁移数据库上的行为。
