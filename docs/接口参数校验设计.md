# 接口参数校验

后端使用 `buf.validate` 声明规则，Core 的 `server/middleware/validate.go` 在 HTTP 和 gRPC 业务处理中调用 protovalidate。校验失败时返回 `INVALID_ARGUMENT`，响应边界按请求语言本地化第一条 violation 的 `message`；错误 reason 和 metadata 保持稳定。

管理端 `ProForm` 的 `rules` 用于即时交互提示，不能替代服务端校验；两端约束应表达同一业务规则。

Core 会把 Protovalidate 的标准规则 ID（例如 `string.email_empty`）统一转换为公共校验消息键，再按请求语言和默认语言回退；不要让标准规则默认英文消息直接返回客户端。

## Proto 写法

```proto
import "buf/validate/validate.proto";
import "gnostic/openapi/v3/annotations.proto";

message ExampleForm {
  string name = 1 [
    (gnostic.openapi.v3.property) = {description: "名称"},
    (buf.validate.field).cel = {
      id: "example.name.required"
      message: "请输入名称"
      expression: "this.size() > 0"
    },
    (buf.validate.field).cel = {
      id: "example.name.max_len"
      message: "名称不能超过 30 个字符"
      expression: "this.size() <= 30"
    }
  ]; // 名称
}

message CreateExampleRequest {
  ExampleForm example = 1 [
    (gnostic.openapi.v3.property) = {description: "示例表单"},
    (buf.validate.field).required = true
  ]; // 示例表单
}
```

规则 ID 使用稳定的 `<resource>.<field>.<rule>`，中文消息直接面向用户。不要依赖生成器默认英文错误。

## 常用规则

| 约束 | Proto |
| --- | --- |
| 字符串必填 | CEL `this.size() > 0` |
| 最大长度 | CEL `this.size() <= 30` |
| 正数 ID | CEL `this > 0` |
| 嵌套消息必填 | `(buf.validate.field).required = true` |
| 枚举合法 | `(buf.validate.field).enum = {defined_only: true}` |
| 列表非空 | CEL `this.size() > 0` |
| 列表唯一 | CEL `this.unique()` |
| 邮箱（必填） | `(buf.validate.field).string.email = true` 并单独表达必填约束 |
| 邮箱（选填） | `(buf.validate.field).ignore = IGNORE_IF_ZERO_VALUE` 与 `.string.email = true` |
| URL | `(buf.validate.field).string.uri = true` |
| 正则 | `(buf.validate.field).string.pattern = "..."` |
| 值集合 | `(buf.validate.field).string.in = ["a", "b"]` |

跨字段规则写在 message 级：

```proto
message PeriodForm {
  option (buf.validate.message).cel = {
    id: "period.range"
    message: "结束时间不能早于开始时间"
    expression: "this.end_at >= this.start_at"
  };

  int64 start_at = 1 [(gnostic.openapi.v3.property) = {description: "开始时间"}]; // 开始时间
  int64 end_at = 2 [(gnostic.openapi.v3.property) = {description: "结束时间"}]; // 结束时间
}
```

唯一性、外键存在、租户权限、受保护资源和状态流转依赖数据库或当前身份，必须放 biz，不能伪装成格式校验。

## 租户字段补全

Core 的 `server/middleware/tenant.go` 在认证成功后、Proto 校验前统一处理请求消息中的 `tenant_id` 字段。普通租户省略租户字段时，使用当前登录身份的租户 ID 填充；已传入其他租户时返回 `PERMISSION_DENIED`；默认租户保留未指定状态，由字段校验和业务规则决定。

该处理会递归覆盖请求中的嵌套表单和重复消息，因此用户、角色、岗位、部门等业务不需要分别实现租户补全。更新、删除仍必须在 biz 校验数据库记录的实际租户归属；请求字段补全不能替代资源权限校验。

具有其他业务含义的 `tenant_id` 不应依赖通用补全，例如登录策略中 `0` 表示全局作用域的字段，应由对应 biz 规则处理。MCP、Agent 和进程内调用若绕过 HTTP/gRPC 中间件，必须通过等价的受信调用入口，不能把普通租户的缺省字段直接交给业务写入。

## ProForm 对应

```ts
const fields: ProFormField[] = [
  {
    prop: "name",
    label: "名称",
    component: "input",
    props: { maxlength: 30, showWordLimit: true },
    rules: [
      { required: true, message: "请输入名称", trigger: "blur" },
      { max: 30, message: "名称不能超过 30 个字符", trigger: "blur" }
    ]
  }
];
```

- `required`、长度、范围、格式和列表数量在前端提供即时提示。
- `maxlength`、`min`、`max` 等控件限制应与 rules 和 Proto 一致。
- 后端返回的业务校验消息仍是最终结果，前端不得因为通过表单校验就跳过错误处理。
- `optional` 字段只有有值时才执行格式规则；前端非必填字段也不应无条件添加 `required`。

## 变更检查

1. 修改 Proto 注释、OpenAPI description 和 `buf.validate`。
2. 执行 `make -C backend api` 和 `make i18n`。
3. 按消费端执行 `make -C frontend ts-admin`、`make -C frontend ts-uni-app` 或 `make -C frontend ts-taro-app`；需要一次生成三端时执行 `make -C frontend ts`。
4. 同步 ProForm rules、控件限制和接口错误展示。
5. 执行后端测试与对应前端类型检查。

生成的 Go、OpenAPI 和 TypeScript RPC 不手工修改。
