# 站内信与通知中心

本文描述当前仓库已实现的消息分类、发布、投递、收件箱和三端通知能力。

## 功能范围

- 管理端创建草稿、立即发布或定时发布、撤回和失败重试。
- 按用户、角色、部门、岗位或租户全员选择收件人。
- 收件箱未读数、分页、详情、已读、全部已读、归档、个人隐藏和过期过滤。
- 分类控制是否生成站内收件记录，以及是否发送到已配置的 Provider。
- 管理端、uni-app 和 Taro 共用同一套消息查询接口和消息中心视图。
- 发布和投递具备租户隔离、幂等处理、失败恢复和投递结果记录。

当前不提供私聊/群聊、输入状态、送达回执、任意 HTML/脚本消息和跨租户共享消息。

## 数据模型

| 表 | 作用 |
| --- | --- |
| `base_message_category` | 消息分类、内容格式、收件箱开关、Provider 列表和模板绑定 |
| `base_message` | 标题、正文、动作、租户、发布状态、计划时间和撤回/过期时间 |
| `base_message_dispatch` | 一次发布任务的受众快照、进度、租约和重试状态 |
| `base_message_delivery` | 每个用户收件目标或 Provider 目标的最终投递事实 |
| `base_message_provider` | Provider 类型、启停状态和加密后的凭据 |
| `base_message_template` | 分类与 Provider 对应的标题、正文和变量模板 |

消息和投递记录始终带 `tenant_id`。发布后保存受众快照，后续角色或部门变化不会改变已发布消息的收件人。

## 发布流程

业务代码通过后端的通知发布入口提交消息，不能自行同时写数据库和队列：

```text
校验租户、分类、受众和内容
  -> Message + Dispatch 同一事务提交
  -> 按 dispatch_id 唤醒队列
  -> 分批生成 Inbox/Provider Delivery
  -> 更新进度并通知在线客户端
```

事务提交成功即表示消息已受理。队列暂时不可用时，Dispatch 保持待处理，恢复任务会按 `next_retry_at` 重新投递。每批处理都校验数据库租约，避免多个消费者同时写入同一批。

## 投递状态

Dispatch 负责发布任务，Delivery 负责每个投递目标。常用状态如下：

```text
Dispatch: PENDING -> RUNNING -> COMPLETED
                     └───────> FAILED
Delivery: PENDING -> SENDING -> SENT
                              ├> FAILED
                              └> SKIPPED
```

失败批次按退避时间重试，超过最大次数后标记失败并保留失败原因。缺少手机号、邮箱或第三方账号绑定时，Provider 投递标记为 `SKIPPED`，不影响同一消息的站内收件。

## 收件箱接口

公共服务位于 `backend/api/proto/base/v1/notification.proto`，管理服务位于 `backend/api/proto/system/admin/v1/base_message.proto` 和 `base_message_category.proto`。收件箱查询只使用 `delivery_type=INBOX`，Provider worker 和统计只使用 `delivery_type=PROVIDER`。

客户端只传当前用户的消息流标识，服务端根据认证身份生成租户和用户范围。SSE 只用于提示有新消息或未读数变化，客户端重连后必须回查 Summary/Page，数据库投递记录才是最终事实。

## Provider 投递

分类的 `provider_id` JSON 数组决定 Provider 投递目标。Provider 凭据由敏感字段加密机制保护，发送时按当前启用配置读取；Provider 失败会写入 Delivery 并进入重试流程。

站内信和 Provider 共用 `base_message_delivery`，Provider 目标使用 `user_id=0` 或具体用户 ID 表示投递对象。模板变量在发送前渲染，模板缺失或变量不完整时记录失败原因，不发送未渲染内容。

## 权限与安全

- 发布、撤回、重试和分类管理只允许拥有对应管理端菜单权限的用户。
- 收件箱查询、已读、归档和隐藏始终以认证用户和租户为条件，不接受客户端指定其他用户。
- 消息动作使用稳定 `view_key` 或受控 URL；客户端点击前重新请求目标资源并执行权限校验。
- 标题、正文和动作参数有长度、深度和格式限制，不允许脚本和任意 HTML。

## 验证

```bash
make -C backend gorm-gen
make gen
make check
```

验收至少覆盖：单用户、角色、部门、岗位、租户全员、定时发布、撤回、过期、重复消费、队列恢复、Provider 失败、租户隔离和三端未读数刷新。
