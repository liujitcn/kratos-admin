# kratos-admin 站内信与通知中心设计

> 日期：2026-08-28；状态：设计与实现记录，当前功能已接入。
> **事实**来自当前源码或外部一手资料；**建议**是本项目取舍。
> 本文记录设计边界、实现状态和验收要点，不替代项目的生成链路与版本化迁移。

## 1. 范围与结论

站内信应是“数据库收件箱 + 异步受众展开 + SSE 尽力唤醒”，不是聊天系统，也不能以 SSE 送达作为业务成功。

```text
管理员/业务发布
  -> MySQL: Message + Dispatch 同事务
  -> Redis Streams: 仅投递 dispatch_id
  -> Consumer: 分批解析受众、幂等写 Delivery
  -> SSE: 通知在线客户端 inbox.changed
  -> Client: 回查 Summary/Page，MySQL 为最终事实
```

核心决策：

1. 新增 `Category/Message/Dispatch/Delivery` 四张业务表。
2. Dispatch 同时承担受众规则、Transactional Outbox、执行租约和 fan-out 游标。
3. Delivery 用 `read_at/revoked_at/archived_at/deleted_at` 表达正交状态，不用单一 SENT/READ 状态。
4. 分类使用独立表，承载显示信息和通知策略；分类名称、标题、正文均不写入 `base_i18n`。
5. 用户 API 放 `base.v1.NotificationService`；管理 API 放 `system.admin.v1.BaseMessageService` 和 `BaseMessageCategoryService`。
6. 业务发布通过 `pkg/notification.Publisher`；不允许业务直接双写数据库与 Redis。
7. 沿用当前 Redis Streams Queue，不引入 Asynq。
8. Admin/H5 使用一条共享 SSE；微信小程序首期使用 onShow 刷新和短轮询。

本期包含管理员草稿、定时/立即发布、撤回、投递进度；指定用户、角色、部门、岗位、租户全员；用户分页、详情、已读/未读、全部已读、归档和个人隐藏；三端未读数与实时刷新。

本期不包含私聊/群聊、输入状态、送达回执、外部邮件短信通道、用户通知偏好、任意 HTML/脚本、精确一次承诺和跨租户共享消息。

业务模块只构造 `notification.Message` 并调用 `notification.Publish`。发布端使用租户、来源和幂等键查重，强制要求至少一个受众并校验正文格式；数据库提交成功后即视为发布成功，队列唤醒失败由恢复任务补投。

## 2. 外部研究结论

### 2.1 Redis Streams

**事实：**`XREADGROUP` 将已投递未确认消息放入 PEL，成功处理后需 `XACK`；超时消息可被 claim。`XAUTOCLAIM` 等价于自动化的 PEL 扫描与 claim。`XADD MAXLEN ~` 会近似裁剪旧条目，不能保证未确认负载永不丢。

来源：

- <https://redis.io/docs/latest/commands/xreadgroup/>
- <https://redis.io/docs/latest/commands/xack/>
- <https://redis.io/docs/latest/commands/xautoclaim/>
- <https://redis.io/docs/latest/commands/xadd/>

**建议：**Queue 只保存定位信息；Dispatch 必须能在 Stream 消息丢失、重复、裁剪后重建任务；handler 仅在数据库批次成功后返回 nil。

### 2.2 Outbox 与幂等

**事实：**AWS Transactional Outbox 用同一事务写业务数据和 Outbox，后台再转发，解决数据库与 broker 双写；其文档明确要求消费者处理重复并关注顺序。Azure 同样建议原子保存对象与事件、后台 relay，并以稳定 MessageId/幂等消费吸收重处理。

来源：

- <https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html>
- <https://learn.microsoft.com/en-us/azure/architecture/databases/guide/transactional-out-box-cosmos>
- <https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer>

**建议：**Message 与 Dispatch 同事务；发布 API 返回 PUBLISHING，不等待大广播完成；唯一索引吸收 Queue 重投。

### 2.3 削峰与实时连接

**事实：**Azure Queue-Based Load Leveling 用队列平滑突发；Competing Consumers 以多个消费者并行处理独立消息，但要求幂等并考虑顺序。

来源：

- <https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling>
- <https://learn.microsoft.com/en-us/azure/architecture/patterns/competing-consumers>

**事实：**WHATWG SSE 定义自动重连、`id/retry/Last-Event-ID`；MDN 说明注释可保活，HTTP/1 同源连接数很低，适合复用单连接。

来源：

- <https://html.spec.whatwg.org/multipage/server-sent-events.html>
- <https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events>

**建议：**SSE 只发变化信号；重连后始终回查 Summary/Page，Last-Event-ID 只作短期优化。

### 2.4 收件箱、安全与三端

**事实：**GitHub 将 Read、Done、Save、Unsubscribe 分开，并支持筛选/分组；GitLab To-Do 支持 Done、Undo、Snooze、批量处理，并在资源访问权消失时移除 To-Do。

来源：

- <https://docs.github.com/en/subscriptions-and-notifications/how-tos/viewing-and-triaging-notifications/managing-notifications-from-your-inbox>
- <https://docs.gitlab.com/user/todos/>

**建议：**read 与 archive 分开；首期 archive 表达 Done；点击通知动作时重新校验目标资源权限。

**事实：**OWASP 建议 tenant context 来自认证会话，查询使用 tenant_id + resource_id，缓存键带租户；不可信内容优先输出编码，确需 HTML 才做 sanitization。

来源：

- <https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html>
- <https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html>

**事实：**微信 `wx.request` 通过 `enableChunked/onChunkReceived` 收分块，不是浏览器 EventSource；Taro 和 uni-app 也将 enableChunked 标为微信小程序能力。

来源：

- <https://developers.weixin.qq.com/miniprogram/dev/api/network/request/wx.request.html>
- <https://docs.taro.zone/docs/apis/network/request/>
- <https://uniapp.dcloud.net.cn/api/request/request.html>

**建议：**AI 主动流继续 chunked；站内信小程序首期不维持全局长请求，H5 条件分支使用 fetch SSE。

## 3. 本地现状

- `backend/bootstrap.go` 已暴露 QueueConsumers 与 Streams；Admin 已注册 `base.message.dispatch` 消费者和恢复任务。
- Dispatch 由 `lock_token` 与 `locked_until` 建立 5 分钟数据库租约；Claim、进度写回、失败写回均校验租约 token，恢复任务只重入队等待、待处理和已过期运行中的任务。
- `data.redis` 非空时 `kratos-kit/queue.NewQueue` 实际选择 Redis Streams，即使配置同时存在 memory queue。
- 当前 Redis consumer group 默认 `redisqueue`，consumer 默认 hostname；visibility 60 秒、reclaim 1 秒、并发 10。
- 本地实现用 `XPENDING + XCLAIM` 回收，成功后 `XACK + XDEL`。
- producer 未显式配置时 StreamMaxLength 默认 1000 且近似裁剪，大广播不能依赖它保存全部待办。
- `kratos-core/data.Transaction` 已能通过 context 让多 Repo 共用事务。
- `base_user` 有 tenant/role/dept/post；消息正文保存在 `base_message.content`。
- Admin 已有带 Authorization、Accept-Language 和共享连接的 `fetch-event-source`。
- uni-app/Taro 的 AI：H5 Fetch SSE，微信小程序 chunked；尚无全局通知流。
- Core 两条 SSE 入口都硬拒绝 `user/authuser`：独立 resolver 与 `SSE.Serve`。
- 当前 `SSEStream.Resolve(channelID,userID)` 缺少 tenant/role/完整 Principal。
- transport 支持 Last-Event-ID/Event.ID，但 Core `PublishJSON` 未设置 ID；replay 仅进程内且 TTL 300 秒。

## 4. 领域模型与四表

### 4.1 `base_message_category`

平台统一的消息分类，由默认租户管理员维护；消息正文和收件记录仍按租户隔离：

| 字段组 | 建议 |
| --- | --- |
| 标识 | id、code |
| 显示 | name、icon、color、sort |
| 默认策略 | default_priority、retention_days、allow_archive、allow_delete |
| 生命周期 | status、created_by、updated_by、created_at、updated_at、deleted_at |

约束与索引：

- `unique(code)`；`code` 是业务发布使用的稳定标识，不随名称变化。
- `(status,sort,id)`。
- 默认分类建议 SYSTEM/SECURITY/TASK/BUSINESS；不为每个租户复制分类行，也不使用 `tenant_id=0` 伪共享行。
- 禁用只阻止新消息使用，不影响历史消息；已有 Message 引用时禁止删除，只允许禁用。
- `retention_days=0` 表示采用系统默认保留期；安全分类可禁止个人归档或删除。

### 4.2 `base_message`

逻辑消息及冻结内容：

| 字段组 | 建议 |
| --- | --- |
| 归属 | id、tenant_id、source_type、source、idempotency_key、payload_hash |
| 发送者 | sender_type、sender_id、sender_name |
| 内容 | category_id、priority、title、content、content_format |
| 动作 | action_type、action_target、action_params JSON |
| 生命周期 | status、scheduled_at、published_at、revoked_at、expires_at |
| 进度 | recipient_total、delivered_total、failed_total |
| 并发/审计 | version、created_by、updated_by、created_at、updated_at |

约束与索引：

- `unique(tenant_id,source,idempotency_key)`。
- `(tenant_id,category_id,status,created_at,id)`。
- `(tenant_id,status,created_at,id)`、`(status,scheduled_at,id)`、`(status,expires_at,id)`。
- DRAFT 才能编辑；进入 PUBLISHING 后内容和受众冻结。
- 发布时校验平台分类已启用；Message 保存 category_id，历史展示不受分类后续禁用影响，消息和收件记录继续校验 tenant_id。
- 主语言标题/正文必填；动作不是授权凭据。

### 4.3 `base_message_dispatch`

受众规则 + Outbox + fan-out 游标：

| 字段组 | 建议 |
| --- | --- |
| 归属 | id、tenant_id、message_id |
| 受众 | audience_type、audience_id、include_children |
| 执行 | status、cursor_user_id、batch_size |
| 计数 | matched_total、inserted_total |
| 重试 | attempt_count、next_retry_at、last_error |
| 租约 | lock_token、locked_until、version |
| 观测 | queued_at、started_at、completed_at、created_at、updated_at |

audience 支持 USER/ROLE/DEPT/POST/TENANT；所有 selector 必须与 Message 同租户，多 selector 取并集。

索引：

- `unique(message_id,audience_type,audience_id,include_children)`。
- `(status,next_retry_at,locked_until,id)`。
- `(tenant_id,message_id,status)`。

### 4.4 `base_message_delivery`

用户收件事实：

- id、tenant_id、message_id、user_id、received_at、expires_at。
- read_at、archived_at、revoked_at、deleted_at。
- created_at、updated_at。

索引：

- `unique(tenant_id,message_id,user_id)`。
- `(tenant_id,user_id,archived_at,deleted_at,id)`。
- `(tenant_id,user_id,read_at,revoked_at,deleted_at,id)`。
- `(tenant_id,message_id,id)`。

状态派生：

```text
visible = deleted_at IS NULL AND revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now)
unread  = visible AND read_at IS NULL AND archived_at IS NULL
```

### 4.5 分类与内容格式

- 分类名称保存于 `base_message_category.name`，图标和颜色由分类表统一提供。
- Message 保存标题和正文主文本，消息分类、标题、正文均不写入 `base_i18n`。
- `base_i18n` 继续只承载既有系统配置、字典、菜单、任务和迁移说明等动态资源。
- 正文支持 PLAIN_TEXT、SAFE_MARKDOWN 和 RICH_TEXT；RICH_TEXT 仅允许编辑器生成的白名单 HTML，展示前必须清洗。

## 5. 状态机

```text
Message:
DRAFT -> SCHEDULED -> PUBLISHING -> PUBLISHED -> REVOKED/ARCHIVED
DRAFT ----------publish----------> PUBLISHING
SCHEDULED --cancel--> DRAFT
PUBLISHING --revoke--> REVOKED

Dispatch:
WAITING -> PENDING -> RUNNING -> PENDING(下一批) -> SUCCEEDED
RUNNING -> PENDING(next_retry_at) / FAILED
WAITING/PENDING/RUNNING -> CANCELLED
FAILED -> PENDING(人工重试)
```

- PUBLISHING 表示可靠待办已提交但受众未完全展开。
- PUBLISHED 表示所有 Dispatch 成功，不表示用户在线接收。
- 部分 Dispatch 失败时 Message 保持 PUBLISHING 并显示失败进度。
- REVOKED 在同一事务按 message_id 更新 Delivery.revoked_at，确保查询和未读立即排除；若压测证明大广播批量更新锁持有不可接受，再引入 REVOKING 与分批收敛状态。

## 6. Proto 与发布接口草案

### 6.1 `base.v1.NotificationService`

统一前缀 `/api/v1/base/notification`：

- `PageInbox`：GET，游标分页；视图 INBOX/UNREAD/ARCHIVED，可按 category/priority 过滤。
- `GetNotification`：GET `/{delivery_id}`。
- `GetInboxSummary`：GET `/summary`，返回 unread_total、category_unread、latest_delivery_id。
- `MarkRead/MarkUnread`：PUT/DELETE `/{delivery_id}/read`。
- `MarkAllRead`：PUT `/read`，请求带 `before_delivery_id` watermark，避免执行期间新消息被标读。
- `Archive/Restore`：PUT/DELETE `/{delivery_id}/archive`。
- `DeleteNotification`：DELETE `/{delivery_id}`，仅设置个人 deleted_at。

用户 API 不接受 tenant_id/user_id；均从认证上下文派生。

### 6.2 `system.admin.v1.BaseMessageService`

统一前缀 `/api/v1/admin/base/message`：

- `PageBaseMessage/GetBaseMessage/CreateBaseMessage/UpdateBaseMessage/DeleteBaseMessage`，删除仅允许草稿。
- `PublishBaseMessage/ScheduleBaseMessage/CancelBaseMessageSchedule/RevokeBaseMessage/RetryBaseMessageDispatch`。
- Form 包含主内容、audiences、version。
- Detail 返回 Message 计数和每条 Dispatch 的状态、游标、attempt、脱敏错误。

权限拆分 list/get、create/update/delete、publish/schedule、revoke、retry。

### 6.3 `system.admin.v1.BaseMessageCategoryService`

统一前缀 `/api/v1/admin/base/message-category`：`PageBaseMessageCategory/GetBaseMessageCategory/CreateBaseMessageCategory/UpdateBaseMessageCategory/DeleteBaseMessageCategory/SetBaseMessageCategoryStatus`；删除前检查 Message 引用，已引用分类返回 CONFLICT。分类仅由默认租户管理员维护，其他租户只读使用。

### 6.4 `pkg/notification.Publisher`

窄接口 `Publish(ctx, Command) (messageID,error)`；Command 包含 tenant、source、idempotency、categoryCode、priority、内容、action、audiences、expiresAt。Publisher 在事务内按 categoryCode 解析平台已启用分类，不向业务调用方暴露 category_id。

- ctx 已绑定事务时加入同一事务，否则自建事务。
- 成功只表示 Message/Dispatch 已提交。
- 同幂等键同内容返回已有 ID；内容不同返回 CONFLICT。
- 业务不得直接 `queue.AddQueue` 或拼 SSE stream ID。

## 7. 事务、Queue 与 fan-out

发布事务：

```text
BEGIN
insert Message(PUBLISHING/SCHEDULED)
insert Dispatch(PENDING/WAITING) per audience
COMMIT
best-effort wake Relay
```

Relay 扫描 PENDING、到期 WAITING、租约过期 RUNNING，向 stream `base.message.dispatch` 投递：

```json
{"dispatch_id":123,"tenant_id":1,"expected_version":7}
```

Consumer 单批流程：

1. 按 id+tenant 加载 Dispatch/Message；终态任务直接 ack。
2. CAS 获取数据库租约；旧 version 或未过期 RUNNING 不推进。
3. 按 `tenant_id AND user.id > cursor ORDER BY id LIMIT batch_size` 查用户 ID。
4. 事务内批量 insert-ignore Delivery，按数据库真实新增行数更新 cursor/count/version/status，重复投递不会重复累加统计。
5. 提交后尽力发 SSE；有下一批则尽力再入队。
6. 入队失败时 Dispatch 仍为 PENDING，Relay 补投。
7. handler 成功返回后 Core 执行 XACK+XDEL。

失败批次先释放租约并进入 PENDING，按 1、2、4、8 分钟指数退避；第 5 次尝试失败后进入 FAILED，由管理端人工重试并重置本轮尝试计数。恢复任务只扫描到期的 `next_retry_at`，不会热循环抢占未到重试时间的任务。

初始 batch_size 500；handler 目标小于 visibility timeout 一半。Queue 全局并发默认 10，站内信有效并发先限制 2-4，压测后调节。

发布时冻结的是受众 selector；具体成员在异步 fan-out 查询时确定，已写入的 Delivery 永不随角色/部门变化。若产品要求严格的“点击发布瞬间成员快照”，必须增加成员历史或先物化全部用户，本期不承诺。多个 selector 重叠由 Delivery 唯一键去重。

## 8. SSE 授权与可靠性

不能只删除 Core 的 user/authuser 拒绝，否则 App 用户可能订阅运维流。

认证后构造 Principal：user_id、tenant_id/code、role_id/code、terminal、session/token、expires_at；全部来自已验证 token。

将 `Resolve(channelID,userID)` 演进为等价的 `AuthorizeAndResolve(request,principal,channelID)`：

| 流 | 策略 |
| --- | --- |
| base.notification | 任意已认证用户；服务端派生 tenant+user stream |
| codegen | 后台用户且任务 owner |
| ops-monitoring | 后台用户且具备对应 Operation/Casbin 权限 |
| runtime-console | 后台用户且具备运行日志权限 |

独立 `/events` resolver 与 Proto `SSE.Serve` 必须复用同一授权实现。

客户端只传 `stream=base.notification`；服务端生成 `base.notification:{tenant_id}:{user_id}`，不接受目标 user channel。

- 使用 Authorization header，不在 URL 放 token。
- 401/403 不重试；网络错误退避重连。
- 单连接 20-30 秒保活，设置最大连接寿命并在 token 过期前重认证。
- 事件 `inbox.changed` 只含 change_type、delivery_id、message_id；客户端 debounce 后回源。
- 当前 replay 仅内存且 Publisher 不设 Event.ID，首期不以 Last-Event-ID 保证正确性。

多实例时 Consumer 节点未必持有用户连接。阶段二可用 Redis Pub/Sub 广播 `notification.changed` 给所有应用节点，各节点只推本地连接；Pub/Sub 丢失仍由数据库对账修复。不能用同一 Queue consumer group 做节点广播。

## 9. 多租户与内容安全

- 所有 Delivery 查询自动带认证 tenant_id+user_id；不存在或越权统一 RESOURCE_NOT_FOUND。
- 普通租户管理员只能选本租户 user/role/dept/post。
- 超级管理员跨租户广播时为每个租户创建独立 Message，不使用 tenant_id=0。
- cache key 必须含 tenant+user，缓存永不参与授权。
- 点击 VIEW_KEY/URL 时目标资源重新鉴权。
- 首期建议只开放 VIEW_KEY；稳定 viewKey 经三端模块映射，不接受组件文件路径。
- title 最大 200，content 建议最大 20KB；action JSON 限深度、键值长度和总大小。
- 禁止未经清洗的 `v-html`、`dangerouslySetInnerHTML`、javascript/data URL；富文本展示必须经过 HTML 清洗，外链若开放仅 HTTPS allow-list。
- 日志不记录 token、完整正文、敏感 action 参数或完整用户数组。

## 10. 三端 UX

通用：badge 99+；列表按 Delivery ID 倒序游标分页；全部/未读/已归档；分类筛选；批量已读；详情显示来源、时间和明确动作。read 与 archive 独立，多设备状态变化后回源。

Admin：Header 铃铛 + 最近 5 条 Popover + 查看全部；一条共享 SSE；管理页沿用 `ProTable + FormDialog + ProForm`，草稿可编辑，发布后只读，展示 Dispatch 进度/失败重试。

uni-app：System module 自包含页面、API 和未读 store；“我的”显示入口与 badge；H5 用 fetch SSE；微信 `onShow`、登录完成、回前台、进消息页刷新，页面可见时 30-60 秒轮询，后台停止。core 不依赖通知业务。

Taro：与 uni-app 相同业务语义；System module 自包含页面、API 和 Zustand 状态；H5 SSE、weapp 轮询；动作通过稳定 viewKey 导航。core 不依赖通知业务。

客户端不永久累加 `unread_delta`：SSE/轮询只触发 Summary，避免重复、乱序和多设备导致计数漂移。

## 11. 容量与保留

Delivery 是容量主导项：`rows = sum(message unique recipient count)`。例如 100 租户 * 1000 用户 * 每月 10 次全员广播 = 100 万行/月。若行和索引约 300-600 字节，则约 300-600MB/月，实施时用真实 MySQL 测量。

未读数首期查 MySQL：tenant+user、read_at NULL、archived/deleted/revoked NULL，并过滤 Message 撤回/过期。只有指标证明需要后才加 Redis cache；cache miss 回源并提供重算/漂移监控。

建议保留：普通 180 天；安全/合规 365 天或按法规；无更新草稿 90 天；FAILED Dispatch 至少 30 天。清理按 1000-5000 行小批：Delivery -> Dispatch -> Message。首期不做分区，数千万行且清理成为瓶颈后再评估。

## 12. 失败恢复与监控

| 故障 | 收敛方式 |
| --- | --- |
| COMMIT 后入队前崩溃 | Relay 扫描 PENDING |
| Redis 不可用 | Dispatch 留库，退避重试 |
| Consumer 崩溃 | PEL reclaim + DB 租约到期 |
| 批次提交后 ack 前崩溃 | cursor/version + Delivery unique 幂等 |
| Stream 被裁剪 | Dispatch 重建 Queue 任务 |
| SSE 无流/缓冲满/断线 | onopen/onShow/Page/Summary 回源 |
| Dispatch 重试耗尽 | FAILED + 脱敏错误 + 人工 Retry，不重置 cursor |

关键指标：Message created/published/revoked；Delivery inserted；Dispatch pending/running/failed、oldest pending、batch duration、retry；Redis stream length、PEL、oldest idle、claim、XADD/XACK 错误；SSE 连接、401/403、TryPublish false、reconnect；Summary/Page 延迟。

告警：oldest pending >5 分钟、FAILED 新增、PEL 持续增长、stream 长度达 max 80%、claim 突增、跨租户拒绝突增、SSE 重连风暴、未读查询慢。

日志字段：message_id、dispatch_id、tenant_id、audience、cursor、batch_size、attempt、queue_message_id、trace_id、error_class。

## 13. 验证矩阵

- 同幂等键并发发布仅一 Message；重叠受众仅一 Delivery。
- Redis 停机时发布，恢复后 Relay 最终投递。
- handler error 留 PEL；超时后 claim；提交后 ack 失败不重复 Delivery。
- 小 max length 强制裁剪后仍能由 Dispatch 恢复。
- 多实例竞争同一 Dispatch 只有有效租约推进。
- 租户 A/用户 A 查询其他租户/用户 delivery 返回 RESOURCE_NOT_FOUND。
- MarkAllRead watermark 不标读执行期间新消息。
- 撤回立即从查询/未读排除，后台补 revoked_at。
- admin/authuser/user 可订阅 notification，但 user 不可订阅运维流；两条 SSE 入口一致。
- 断线、缓冲满、多标签页、多设备操作后 Summary 收敛。
- Admin 亮/暗/灰/色弱；uni/Taro H5 SSE；微信 onShow/轮询/分页/viewKey。
- 1、100、1万、10万受众压测；百万 Delivery 的 Summary/Page EXPLAIN；广播时普通 CRUD 和连接池稳定。

## 14. 分阶段实施

阶段 0：冻结四表/状态/API；确认分类策略、有效用户、部门子树、保留期；用临时数据验证索引和 batch。

阶段 1：四表、默认分类、迁移/GORM Gen、Publisher、USER/TENANT、Outbox Relay、Redis Consumer、用户 API、三端收件箱与小程序刷新；验收 Redis 故障恢复和租户隔离。

阶段 2：消息与分类管理、定时/撤回/重试、ROLE/DEPT/POST、过期收件清理、监控、Admin Header；验收万人广播和失败可恢复。

阶段 3：Core Principal/流级授权、notification SSE、Admin/H5 共享连接、重连对账；验收 user/authuser 可收通知但不能访问运维流。

阶段 4：Redis Pub/Sub 多节点唤醒、按指标增加 unread cache/限速/分区，再考虑 Save、Snooze、偏好和外部通道。

## 15. 明确不做

- 不以 SSE 成功定义投递成功，不以 Redis Stream 作为永久消息库。
- 不引入 Asynq/Kafka/第二套队列，不在 Queue 失败时退化为无监管 goroutine。
- 不为每用户创建 Redis Stream，不把大用户数组放进 Queue。
- 不同步完成全员 fan-out 后才返回 HTTP。
- 不让客户端决定 tenant/user stream，不用 query token。
- 不混合 read/archive/revoke/delete，不原地修改已发布消息。
- 不让通知绕过业务权限，不支持任意 HTML/脚本/组件路径。
- 不提前建设模板市场、复杂规则引擎或多通道平台。

## 16. 待确认产品项

1. 禁用用户是否收新消息；建议不收且恢复后不补历史广播。
2. DEPT 是否默认含子部门；建议显式选择。
3. 过期消息是否可查历史；建议主收件箱隐藏、管理审计保留。
4. 用户个人删除是否恢复；建议首期不可恢复但只软隐藏。
5. 安全类消息能否个人删除；建议保留期内不可删除。
6. 180 天默认保留是否满足法规。
7. 外链是否首期开放；建议只支持 VIEW_KEY。
8. 跨租户人工广播是否首期开放；建议不开放。

最终边界：MySQL Delivery 是事实，Dispatch 是可恢复 Outbox/游标，Redis Streams 是异步执行载体，SSE 是在线优化，客户端回源构成最终一致性闭环。
